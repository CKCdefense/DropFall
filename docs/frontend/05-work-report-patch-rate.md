# 작업 보고서 — patchRate 미설정으로 60Hz 상향분이 전달되지 않던 문제

> [backend/12~14](../backend/)(보간·틱레이트 상향·외삽) 리뷰 중 발견. 코드 자체는 문제없고,
> Colyseus 설정 하나가 빠져 있었다.

## 문제

[backend/13](../backend/13-work-report-tick-rate-60hz.md)에서 `TICK_RATE`를 20 → 60으로 올렸다.
그런데 **클라이언트가 실제로 받는 상태 갱신 주기는 그대로였다.**

Colyseus는 두 가지가 완전히 별개다:

| 설정 | 역할 | 기본값 |
|---|---|---|
| `setSimulationInterval(fn, ms)` | 서버가 게임 로직을 계산하는 주기 | 없음(직접 지정) |
| `Room.patchRate` | 계산된 상태를 **클라이언트로 내보내는** 주기 | **1000/20 = 50ms** |

`GameRoom`은 `setSimulationInterval`만 60Hz로 지정하고 `patchRate`를 건드리지 않았다.
결과적으로 **서버는 60Hz로 계산하고 클라이언트는 20Hz로 봤다.**

## 측정

클라이언트를 붙여 `room.onStateChange` 도착 간격을 4초간 측정했다.

| | 도착 간격(평균) | 실효 주파수 |
|---|---|---|
| 수정 전 (`patchRate` 미설정) | 63.1ms | **15.9Hz** |
| 수정 후 (`patchRate = 1000/60`) | 20.3ms | **49.2Hz** |

> 기본값 50ms보다 더 벌어진 63ms가 나온 건 60Hz 시뮬레이션 인터벌과 20Hz 패치 스케줄러가
> 겹치면서 생긴 것으로 보인다. 어느 쪽이든 60Hz와는 거리가 멀다.

## 파생 문제 — 보간 지연이 스냅샷 간격보다 짧았다

`SnapshotInterpolator`는 지연을 **틱 간격의 배수**로 정의했다(`2틱 = 33.3ms`).
스냅샷은 실제로 63ms마다 왔으므로, **보간할 "미래" 스냅샷이 절반은 존재하지 않았다.**

실제 `SnapshotInterpolator`에 63ms 간격 스냅샷을 넣고 60fps로 샘플링해 측정:

| 조건 | 외삽으로 그린 프레임 |
|---|---|
| 수정 전 (도착 63ms / 지연 33.3ms) | **47%** |
| 수정 후 (도착 20.3ms 균일 / 지연 33.3ms) | 0% |
| 수정 후 (실측 지터 11~46ms 혼합) | 12% |

[backend/14](../backend/14-work-report-extrapolation.md)는 외삽을 "지터로 스냅샷이 가끔 늦게
올 때의 안전장치"로 도입했는데, 수정 전에는 **절반의 프레임에서 상시 동작하는 기본 경로**였다.
등속 구간에서는 외삽이 정확해 오차가 작지만(≈2px), 방향 전환·정지 순간마다 오버슛 후
보정이 들어간다. 수정 후에는 지터가 있을 때만(12%) 동작하는, 원래 의도한 역할로 돌아왔다.

## 수정

1. **`shared/constants.ts`에 `PATCH_RATE` 추가** — 지금은 `TICK_RATE`와 같은 값이지만
   **의미가 다른 상수**라 별도로 둔다. 대역폭이 문제가 되면 틱은 그대로 두고 이 값만
   낮추는 것이 일반적인 최적화다.
2. **`GameRoom.onCreate`에서 `this.patchRate = 1000 / PATCH_RATE`** 명시.
3. **`SnapshotInterpolator`의 지연 기준을 `TICK_RATE` → `PATCH_RATE`로 변경.**
   보간은 "도착한 스냅샷 두 개 사이"를 채우는 일이라 서버 내부 틱 수와는 무관하다.

3번이 재발 방지의 핵심이다. 1·2번만 고치면 지금은 맞지만, 나중에 누군가 대역폭 때문에
`patchRate`만 낮추는 순간 같은 문제가 다시 생긴다.

## 남은 것

- **자기 캐릭터도 보간 대상이다** → 내 입력에 `INTERP_DELAY_MS`(33ms)가 그대로 얹힌다.
  클라이언트 예측을 붙일 때 자기 캐릭터는 보간에서 제외해야 한다.
- **`LocalConnection`의 보간은 사실상 불필요하다.** 60Hz 시뮬 + 60fps 렌더라 지연만 늘린다.
  코드 경로를 하나로 유지하는 이득이 더 크다고 보면 그대로 둬도 된다.
- 60Hz 전송의 실제 대역폭은 아직 측정하지 않았다. 4인 룸 기준으로는 문제없어 보이지만,
  엔티티(몬스터·투사체)가 늘어나면 AOI와 함께 다시 볼 것.
