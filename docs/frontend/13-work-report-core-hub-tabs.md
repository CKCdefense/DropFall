# 13. 코어 허브 창 — 탭 통합과 돌 프레임 (작업 보고)

코어 앞에서 열던 창 넷(코어/제작/상점/창고)을 **탭 하나짜리 큰 창**으로 합치고, 로비
UI가 쓰던 돌 프레임(`title_modal.png`)을 인게임 모달에도 9-slice로 입혔다.

## 1. 무엇이 문제였나

- **창이 너무 작았다.** 코어 모달이 220×240이라 정보 세 줄과 버튼 여섯 개로 꽉 찼다.
- **창을 갈아타야 했다.** 코어 모달은 사실상 "다른 창을 여는 버튼 판"이었다. 창고에서
  재료를 확인하고 제작으로 가려면 창을 닫고 다시 열어야 했고, 둘을 같이 띄우면 서로를
  가렸다.
- **인게임 UI만 민무늬였다.** 로비(DOM)는 이미 돌 프레임을 쓰는데 인게임 모달은 단색
  사각형이라 같은 게임처럼 보이지 않았다.

## 2. 구조

```
Modal (공용 뼈대)
 ├ PanelBuilder      — 컨테이너 하나에 행·버튼·칸을 찍어내는 도구
 └ tabs 옵션         — 상단 탭 줄 + 탭 수만큼의 페이지 컨테이너

CoreModal (허브, 700×470)
 ├ 코어 탭    — 직접 그린다(정보 행 + 주입/코어 관리 + AI 대사)
 ├ 제작 탭    — CraftPanel
 ├ 상점 탭    — StorePanel
 └ 창고 탭    — WarehousePanel
```

### 2.1 왜 PanelBuilder를 뽑았나

`addRow`/`addButton`/`addSlot`은 원래 Modal의 protected 메서드였다. 한 창 안에 여러
페이지를 담으려면 "모달"이 아니라 **임의의 컨테이너**에 같은 조각을 그릴 수 있어야 한다.
Modal은 이제 자기 콘텐츠용 빌더를 하나 들고 그 메서드를 그대로 위임한다 — 손대지 않은
기존 모달(코어 관리·개발자 아이템)은 아무 영향이 없다.

`narrow(width)`도 함께 뒀다. 창이 넓어지니 정보 행이 화면 양끝으로 갈라져서, 왼쪽 열
안에서만 좌우로 벌어지게 폭을 좁혀 쓴다.

### 2.2 모달 → 패널 전환

`CraftModal`/`StoreModal`/`WarehouseModal`은 각자 `Modal`을 상속한 **창**이었다. 이걸
`CraftPanel`/`StorePanel`/`WarehousePanel`로 바꿨다 — 창이 아니라 "주어진 빌더에 내용을
그리는 것"이 되면서, 탭 페이지든 어디든 얹을 수 있다. 내부 레이아웃 코드는 그대로다.

바깥(HudScene)에서 보면 창은 하나다. 그래서 각 탭의 콜백·갱신도 허브가 대신 받아 넘긴다
(`onCraft`, `setStoreContext`, `setStorageSlots` …). 어느 탭이 무엇을 담당하는지는 허브
안에서만 알면 된다.

## 3. 돌 프레임(9-slice)

로비 CSS가 이미 `title_modal.png`를 `border-image`로 쓰고 있었다. 같은 파일을 Phaser
텍스처로 한 번 더 올려 인게임 모달의 테두리로 쓴다 — **슬라이스 값도 로비 쪽에서 이미
실측해 둔 것(`tokens.css`의 16)을 그대로 가져왔다.** 두 곳에서 따로 재면 반드시 어긋난다.

두 가지를 조심해야 했다.

- **프레임 안쪽이 밝다.** 그 위에 HUD의 어두운 글자를 얹으면 읽히지 않는다. 테두리만
  남기고 안쪽을 어두운 판으로 덮어 나머지 HUD와 같은 톤을 유지한다.
- **패딩이 테두리보다 커야 한다.** 모달 패딩이 9-slice 테두리 두께(16)보다 작으면 글자가
  돌 테두리 위로 올라탄다. `PAD = FRAME_INSET + 4`로 묶어 뒀다.

에셋이 없으면 조용히 예전처럼 단색 사각형 + 1px 테두리로 떨어진다. 임시 에셋을 끼워
쓰는 단계라 언제든 빠질 수 있다.

## 4. 드래그앤드롭이 걸려 넘어질 뻔한 곳

창고 칸 ↔ 퀵슬롯 드래그는 `SlotDrag`가 처리하는데, 대상 판정에 `box.visible`을 본다.
**Phaser의 `visible`은 자기 자신의 플래그다** — 부모 컨테이너를 숨겨도 자식의 `visible`은
true 그대로다. 즉 제작 탭을 보고 있어도 창고 칸이 여전히 드롭을 받아먹는다.

그래서 등록 조건을 "모달이 열려 있나"에서 **"창고 탭이 보이나"**로 좁혔다
(`coreModal.isWarehouseVisible()`).

실제로 확인했다: 창고 탭에서 퀵슬롯으로 끌면 옮겨지고, 제작 탭에서 같은 자리로 끌면
아무 일도 일어나지 않는다.

## 5. 남은 것

- **코어 관리(티어업)는 아직 별도 창이다.** 와이어프레임의 탭이 넷이라 거기 넣지 않고
  코어 탭의 버튼으로 남겼다. 탭을 하나 더 늘릴지는 UI를 더 채운 뒤에 정하면 된다.
- 모달은 여전히 생성 시점에만 화면 중앙에 놓인다(창 크기 변경에 반응하지 않는다).

## 6. 2차: 서류철 탭과 그리드 레이아웃

1차는 "탭이 동작한다"까지였다. 화면을 보니 두 가지가 걸렸다 — 탭이 그냥 버튼 줄로
보였고, 각 탭 내용이 작은 창 시절 좌표 그대로라 넓어진 판이 아래로 텅 비었다.

### 6.1 탭을 서류철로

버튼이 아니라 **내용 판에 붙은 색인표**로 보여야 한다. 세 가지로 만들었다.

- **높이 38px** (예전 30). 글자 위아래로 숨 쉴 자리가 생겼다.
- **선택된 탭은 판과 이어 붙는다.** 판의 윗변을 2px 덮어써서 경계선을 지운다 —
  이 겹침이 "탭과 판이 한 장의 종이"라는 인상을 만든다.
- **선택 안 된 탭은 5px 내려앉는다.** 뒤에 밀려 있는 서류철 탭을 흉내낸 것이다.

폭도 창을 균등 분할하지 않고 **글자 길이에 맞춘다**. 균등 분할은 어떻게 그려도
버튼 줄로 보인다.

9-slice 그림을 나중에 끼울 때도 이 구조(높이·겹침·앉음)는 그대로 쓴다.

### 6.2 구역 상자로 판을 채운다

와이어프레임의 공통 문법은 "테두리 안에 묶인 한 덩어리"다. `PanelBuilder.addSection`을
두고 세 탭이 같은 여백(12)·같은 간격(10)으로 구역을 나눠 쓴다.

| 탭 | 구성 |
|---|---|
| 제작 | 왼쪽 [Tier 1/2/3] · 오른쪽 [해당 티어 격자] · 아래 [상세 + 제작] |
| 상점 | 왼쪽 위 [진열 격자] · 왼쪽 아래 [상세 + 구매] · 오른쪽 [판매] |
| 창고 | 위 [5×4 격자] · 아래 [고른 칸 + 폐기] |

**아래쪽 구역은 남은 높이를 전부 쓴다.** 고정 높이로 두면 판 아래가 통째로 빈다.
칸 크기도 키웠다(창고 40→62, 진열/제작 48→62).

제작은 **티어를 먼저 고르고 그 안에서 물건을 고르는** 구조로 바꿨다. 예전엔 전체
레시피를 한 격자에 쏟아 놓고 칸마다 T1/T2/T3를 작은 글씨로 적었는데, 지금 만들 수 있는
게 무엇인지 한눈에 안 들어왔다. 티어가 목록을 가르는 축이면 "코어를 올리면 무엇이
열리는가"도 같이 보인다. 잠긴 티어는 버튼을 흐리게만 하고 감추지 않는다.

여기서 하나 걸렸다: 위 구역 높이를 격자만 보고 잡았더니 **티어 버튼이 셋일 때 마지막
버튼이 상자 밖으로 나가 아래 구역에 가려졌다.** 격자와 티어 열 중 큰 쪽으로 잡는다.

### 6.3 폐기

창고 와이어프레임에 있던 버튼이다. 눌리지 않는 장식을 두느니 실제로 동작하게 했다.

**없애지 않고 바닥에 떨군다.** 창고가 꽉 차서 자리를 만드는 게 목적인데, 아주 지우면
잘못 누른 순간 되돌릴 방법이 없다. 바닥에 나오면 마음이 바뀌었을 때 다시 주우면 되고,
"자리를 비운다"는 목적은 그대로 달성된다. 코어 근접 검사는 창고를 만지는 다른 조작
(moveItem/quickMoveItem)과 같은 규칙을 쓴다.

칸을 눌러 고르고 폐기를 누른다. 같은 칸을 다시 누르면 선택이 풀린다 — 고른 채로 두고
실수로 폐기를 누르는 일을 줄인다. 드래그(옮기기)와 클릭(고르기)은 같은 사각형 위에서
서로 방해하지 않는다.

**구현 중에 잡은 버그**: `slotAt`은 살아 있는 칸을 그대로 돌려준다. 먼저 지우고 그
참조로 떨어뜨리면 `count`가 이미 0이라 아무것도 안 나온다. 비우기 **전에** 내용을
복사해 둔다.

## 7. 로비 폼 모달 비율

로비 모달은 셋(방 목록 / 방 만들기 / 코드로 참가)이 **한 벌의 크기**를 공유하고 있었다
— `--modal-w 760 × 비율 1.55`. 그 값은 **방 목록 표**에 맞춘 것이다(방코드·방 이름·인원·
참가 네 열). 입력 두 칸과 버튼뿐인 폼이 같은 상자를 쓰니 좌우가 통째로 비고 글자만
왼쪽에 붙어 있었다.

폼만 세로로 선 비율(`420 × 0.92`)로 갈랐다. **크기 공식은 그대로 재사용한다** —
`.modal-form`에서 `--modal-w`/`--modal-ratio`만 덮어쓰면 `.modal`의 폭·비율·높이 상한
계산이 그대로 적용된다. 공식을 두 벌 두면 반드시 어긋난다.

내부도 와이어프레임대로 세웠다.

- 제목은 가운데. 폼은 좌우 대칭이라 제목만 왼쪽이면 축이 어긋나 보인다.
- 버튼은 세로로 쌓고 폭을 꽉 채운다. 좁은 상자에서 둘을 나란히 두면 각각이 글자보다
  조금 큰 정도로 쪼그라들어 누르기도 읽기도 나빠진다.
- 코드 4칸을 폼 폭에 맞춰 벌린다(`space-between`). 가운데 정렬로 두면 아래 비밀번호
  입력창과 좌우 끝이 어긋나 두 덩어리가 따로 노는 것처럼 보인다.
- 코드 참가 화면에도 제목("코드로 참가")을 붙이고, 비밀번호에 라벨을 달았다. 라벨이
  생겼으니 자리표시자의 "비밀번호:"는 다른 안내로 바꿨다(같은 말을 두 번 쓰지 않는다).

**방 목록은 그대로 760×490**이다. 표는 가로가 필요하다.

곁들여 고친 것: `.code-form-label`("방 코드")이 9-slice 에셋용 색 반전 목록에서 빠져
있어서, 밝은 프레임 안쪽에서 거의 안 보였다.
