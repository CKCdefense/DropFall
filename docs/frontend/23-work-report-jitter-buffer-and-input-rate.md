# 23. 지터 버퍼 시간 기준 고정 + 입력 전송률 드리프트 수정 (작업 보고)

"같이 하는 사람은 멀쩡한데 나만 화면과 몹이 순간이동한다"는 제보에서 출발한 넷코드
전체 점검. 결함 두 개를 고쳤고, 진짜 원인 후보(릴레이 경유)는 인프라 쪽 후속 작업으로
남긴다.

## 1. 제보를 그대로 믿지 않고 경로부터 쟀다

증상만 보면 회선 문제 같지만, 방향이 이상했다 — **서버가 제보자의 집에 있는데** 밖에
있는 사람이 멀쩡하고 집에 있는 사람이 끊긴다. 서버가 밀리면 둘 다 밀려야 하고, 회선이
문제면 밖이 더 나빠야 한다.

플레이 PC에서 실측하니 답이 나왔다. `nslookup lab.tailcecca7.ts.net`이 **공개
릴레이 IP**(103.84.155.x)를 돌려줬다 — Tailscale Funnel은 모든 공개 트래픽을
자기네 해외 엣지에서 받아 터널로 넘기므로, 서버가 옆방에 있어도 패킷이 해외를 한 바퀴
돌고 **집 회선을 두 번 통과한다**. 같은 집이라는 이점이 없다. curl 15회 실측: TCP 연결
RTT 14.7~40.8ms(평균 ~24ms) — 왕복이면 기본 ~50ms에 순간 26ms씩 흔들린다.

그 흔들림이 왜 "순간이동"으로 보이는가가 이 작업의 코드 쪽 몫이다.

## 2. 지터 버퍼가 PATCH_RATE에 묶여 40ms까지 좁아져 있었다

보간 지연이 `2 × 1000 / PATCH_RATE`였다. 20Hz 시절엔 100ms였는데, 압축을 켜고
PATCH_RATE를 50Hz로 되올리면서(docs/backend/57·58) **지터 허용치가 40ms로 같이
줄었다** — 아무도 그걸 의도하지 않았다. 전송 주기는 대역폭의 문제고 버퍼는 회선
안정성의 문제인데, 상수 하나에 묶여 "자주 보낼수록 흔들림에 약해지는" 거꾸로 된
관계가 됐다.

40ms를 넘는 지연 스파이크마다: 보간할 미래 스냅샷이 없음 → 100ms까지 외삽 → 정지 →
밀린 패치가 몰려 도착하면 한 번에 따라잡음. 이게 "몹 텔레포트"의 정체다.

### 수정 — 시간 기준 120ms 고정, 하한만 PATCH_RATE 기준

```ts
export const NETWORK_INTERP_DELAY_MS = Math.max(120, (2 * 1000) / PATCH_RATE);
```

120ms를 겁내지 않아도 되는 근거: 내 캐릭터는 예측(`PlayerPredictor`)으로 즉시
그려져 이 지연과 **무관하다**. 대가는 원격 엔티티가 120ms 늦게 보이는 것뿐이고, 협동
PvE라 다른 플레이어를 정밀 조준할 일이 없다. 예측이 없던 시절엔 이 지연이 곧 조작
지연이라 줄일 이유가 있었지만(docs/backend/47의 왕복), 지금은 그 제약이 사라졌다.

오프라인은 따로 50ms를 쓴다(`LOCAL_INTERP_DELAY_MS`, 생성자 인자). 지터가 없는
전송에 온라인 버퍼를 쓰면 몬스터만 이유 없이 늦게 보인다 — docs/backend/47이
"오프라인 미세 최적화 여지"로 남겨둔 바로 그것이다.

## 3. 입력 전송률이 고주사율에서 조용히 떨어지고 있었다

`InputController.update`의 전송 타이머가 주기를 넘기면 `elapsed = 0`으로
리셋했다 — 나머지가 매번 증발한다. 60Hz 모니터에선 프레임(16.7ms)과 주기(16.7ms)가
거의 같아 티가 안 나지만, **144Hz면 6.9ms×3 = 20.8ms마다 보내고 4.2ms를 버려 실효
48Hz**가 된다.

서버는 "마지막 입력을 매 틱 반복 적용"하므로 이동 속도는 안 변한다. 문제는 예측 쪽이다
— `PlayerPredictor`는 전송 1회당 고정 스텝(1/60초)씩만 전진하므로, 48Hz로 보내면
예측 기준점이 서버보다 초당 20% 덜 가고, 재조정마다 앞으로 당겨진다. **고주사율
모니터에서만 보이는 상시 고무줄**이다. 제보자 환경이 여기 해당하면 "나만 이상하다"의
한 조각일 수 있다.

수정: `elapsed %= SEND_INTERVAL_MS` — 나머지를 이월하되, 큰 프레임 드랍 뒤 밀린
횟수만큼 몰아 보내지는 않는다(놓친 주기의 입력은 서버가 어차피 반복 적용했다).

## 4. 점검에서 통과한 것들

전체 넷코드(연결·보간·예측·입력·서버 전송·시뮬 입력 적용)를 훑었고 아래는 건드릴
필요가 없었다: 입력 seq 역전 가드(world.setInput), 재조정의 원본 패치 쌍 사용
(getRawPlayer), 각도 최단경로 보간, 외삽 상한·장애물 관통 차단, FixedStepAccumulator의
따라잡기 상한, 클라이언트 쿨다운의 비관 판정, patchRate 명시 설정.

## 5. 남은 것

- **인프라(진짜 원인)**: Funnel 릴레이 우회 — 도메인 구입 후 Cloudflare Tunnel(국내
  엣지)로 교체 예정. 무료 DERP 릴레이는 지연·지터·처리량 모두에서 병목이고, 과거
  "2인 접속부터 밀렸다"(docs/backend/47)의 진범도 대역폭이 아니라 릴레이였을 가능성이
  높다.
- **도착 시각 타임스탬프**: 버퍼가 패치 도착 시각(`performance.now()`) 기준이라 TCP
  재전송으로 패치가 몰려 도착하면 시간축이 압축돼 빨리감기처럼 재생된다. 120ms 버퍼가
  대부분 흡수하지만, 근본 해결은 스냅샷에 서버 틱 번호를 실어 서버 시간축으로 배치하는
  것이다.
- **보간 비용**: 패치마다 전 엔티티 깊은 복사(50Hz) + `blendList`의 `find` 선형
  탐색(O(n²)). 후반 웨이브 몬스터 수백 마리면 프레임 드랍 기여자다 — id→객체 Map으로
  바꾸면 O(n).
- **실접속 재검증**: 이번 수정은 타입체크·린트로만 검증했다(코드 성격상 상수와 산술
  변경). 120ms 체감과 순간이동 소멸 여부는 다음 멀티 세션에서 확인해야 한다.
