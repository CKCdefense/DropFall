# 작업 보고서 — 티모시가 코어에 막혀 영원히 멈추는 이동 버그

> 티모시(AI 동반자)의 이동은 축 슬라이딩(전체→X만→Y만) 2단계 폴백만
> 있었다 — 몬스터가 자원 노드/콜로니에 막히던 것과 같은 종류의 버그
> (docs/backend/40)가 코어를 상대로도 그대로 있었던 것. 코어를 정면으로
> 마주 보는 경로(특히 정확히 수평/수직인 경로)에서 영원히 멈췄다.

---

## 1. 기획 — 무엇을, 왜

원문 요청: "티모시 이동로직관련해서 코어가 막고있으면 막혀서 이동을
못하는 문제 해결해줘".

## 2. 과정 — 어떻게 했나

### 2.1 원인 — 몬스터는 이미 고친 버그를 티모시는 못 물려받았다

`moveCompanionToward`는 `movePlayer`와 같은 2단계 폴백(전체 이동 → X축만
→ Y축만)만 쓰고 있었다. 몬스터는 이미 docs/backend/40에서 3단계째(접선
미끄러짐)와 docs/backend/42에서 탈출 점프까지 갖췄는데, 티모시 이동
함수는 그 이전 버전 그대로였다.

**실측 재현**: 티모시를 코어 서쪽(-70,0)에 두고 코어 동쪽(70,0)의 자원
노드로 보내면, 정확히 코어 서쪽 벽 앞(-62.67,0)에서 멈춰 선 채 있었다.
정확히 수평인 접근이 특히 나쁜 경우다 — X축 이동은 벽을 그대로 파고들어
막히고, Y축은 방향 성분이 정확히 0이라(`dirY === 0`) 애초에 시도조차
안 된다.

**왜 자주 겪는 문제인가**: 티모시가 자원 노드로 갈 때(`traveling`)와
코어로 돌아갈 때(`returning`, 목적지가 코어 원점 그 자체) 둘 다 이 함수를
쓰는데, 코어는 항상 맵 중앙에 있어서 어느 방향으로든 이동하다 보면 경로가
코어를 스치거나 관통하는 경우가 잦다.

### 2.2 수정 — 몬스터의 해법을 그대로 이식

- `CompanionEntity`에 `stuckSeconds` 필드 추가(몬스터의 것과 같은 용도).
- `findNearestObstacleCenterForPlayer(x, y)` 신규 — 몬스터용
  `findNearestObstacleCenter`(자원 노드/콜로니만 봄)와 달리, 플레이어/
  티모시가 실제로 막히는 대상(이동을 막는 건축물, 자원 노드, 콜로니,
  **코어**)을 전부 다룬다. 코어는 8각형이라 접선 방향 계산엔 원점을
  중심으로 근사했다(받침대가 원점 대칭에 가깝게 설계돼 있어 충분하다 —
  거리 자체는 `coreDistance`가 실제 윤곽 기준으로 정확히 잰다).
- `moveCompanionToward`에 3단계째(접선 미끄러짐)와 탈출 점프
  (`tryEscapeStuckCompanion`, `tryEscapeStuckMonster`와 같은 로직)를
  추가했다. `dirX/dirY`가 정확히 0인 축은 "이동 시도 자체가 없었다"로
  보고 그 축 결과를 인정하지 않는 안전장치도 몬스터 버전과 동일하게
  가져왔다.

## 3. 결과 — 검증

`companion.test.ts`에 회귀 테스트 3개 추가:
- 코어를 정면으로(수평) 관통하는 경로로 자원 노드를 찾아가는 케이스 —
  **수정 전 코드로 먼저 실행해 실제로 실패하는 것을 확인**한 뒤(-62.67,0
  에서 영원히 멈춤), 수정 후 통과하는 것까지 확인했다.
- 같은 관통 경로로 코어에 복귀하는 케이스.
- 코어 주변 16개 각도에서 복귀를 시작해도 전부 도달하는 스윕 테스트.

```bash

pnpm --filter @dropfall/server typecheck
pnpm --filter @dropfall/server test        # 31/31
pnpm --filter @dropfall/client typecheck
pnpm lint
```
