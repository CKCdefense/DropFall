# 작업 보고서 — 총알 궤적(그림)과 실제 피격 위치가 어긋나던 버그 수정

> "총알 궤적 이미지랑 실제 피격이 다른 것 같다"는 제보를 받고 코드를 뜯어보니,
> 투사체를 그릴 때 판정 좌표와 무관하게 화면에서만 위로 18px(월드 단위) 띄워서
> 그리고 있었다 — 총구 이펙트 높이에 맞추려던 연출이었는데, 몬스터는 그런 오프셋
> 없이 실제 좌표 그대로 그려지다 보니 "보이는 궤적"과 "실제 맞는 자리"가 날아가는
> 내내 어긋나 있었다.

---

## 1. 기획 — 무엇을, 왜

backend/32에서 "돌진형 몬스터를 못 맞힌다"는 제보를 고친 직후, "지금 나가는 총알
궤적이미지랑 실제 총알 피격이 다른거같아"라는 제보를 또 받았다. 이번엔
backend/32와 달리 판정 자체(원거리 사격이 실제로 맞는지)가 아니라, **화면에
보이는 총알 위치**가 실제 판정 위치와 다르다는 지적이었다.

## 2. 과정 — 어떻게 했나

`EntityRenderer.syncProjectiles()`를 보니 투사체를 그릴 때마다 매번 이렇게
그리고 있었다:

```ts
sprite.setPosition(Math.round(projectile.x), Math.round(projectile.y) + PROJECTILE_LIFT);
```

`PROJECTILE_LIFT = ORBIT_CENTER_Y - 4 = -18` — 총알을 화면상 y축으로 18px(카메라
줌 2배 기준 화면 36px) 위로 띄워서 그리고 있었다. 주석을 보니 의도는 있었다:
"총구·휘두르기 이펙트와 같은 가슴 높이 평면에 올린다"— 총구 섬광이 캐릭터 가슴
높이에 그려지는데, 총알만 판정 좌표(발밑 기준 평면) 그대로 그리면 총구가 아니라
허리께에서 나가는 것처럼 보여서 넣은 보정이었다.

문제는 이 오프셋이 **발사 순간 한 번이 아니라 날아가는 내내, 화면에만** 적용된다는
점이다. 반면 몬스터는 어떤 오프셋도 없이 실제 좌표(`monster.x/y`) 그대로 그려진다
(backend/31에서 히트박스 반경까지 맞춰놨다). 그러니 화면에 보이는 총알의 궤적은
실제 판정이 이뤄지는 선(월드 좌표 그대로의 직선)보다 화면에서 계속 18px 위로 뜬
평행선이었다 — 총알이 몬스터 머리 위를 스치듯 지나가는 것처럼 보여도 실제로는
몬스터 몸통 한가운데를 관통하고 있었고(맞았는데 안 맞은 것처럼 보임), 반대로
스치듯 맞는 것처럼 보이는 상황에서 실제로는 그보다 한참 위(몬스터 몸에서 먼
지점)를 지나 빗나갔을 수도 있다.

**수정**: `PROJECTILE_LIFT` 오프셋을 완전히 없애고, 투사체를 판정과 똑같은 실제
좌표에 그대로 그리게 했다. "총구에서 막 나가는" 연출은 이미 별도의 총구 섬광
이펙트(`flash`, 무기 궤도 중심 `ORBIT_CENTER_Y` 기준으로 그려짐)가 담당하고
있어서, 날아가는 동안의 총알 자체는 판정선과 정확히 겹치는 쪽이 — 특히 원거리
무기가 실제 전투에 쓰이는 게임에서는 — 조준 신뢰도에 훨씬 더 중요하다고 판단했다.
쓰지 않게 된 `PROJECTILE_LIFT` 상수와 `ORBIT_CENTER_Y` import도 같이 지웠다.

## 3. 결과 — 검증

```bash
pnpm --filter @dropfall/shared test     # 180 passed, 변경 없음(순수 클라이언트 렌더링만 수정)
pnpm typecheck                          # client/server 전체 통과
pnpm lint                               # 에러 0(안 쓰는 import 제거 확인)
pnpm build                              # client(vite)/server(tsup) 전체 통과
```

Playwright로 총구 섬광이 여전히 가슴 높이에 정확히 그려지는 것은 확인했다.
날아가는 총알 자체가 판정선과 겹쳐 그려지는지는, 총알 속도(420px/s)가 빨라서
자동화 브라우저의 스크린샷 왕복 시간 안에 붙잡기가 어려워(매번 화면 밖으로
사라진 뒤에야 스크린샷이 찍혔다) 픽셀 단위로 직접 캡처하지는 못했다 — 대신
코드 변경 자체가 아주 단순하고 명확해서(좌표에 상수를 더하던 코드를 완전히
지운 것뿐, 새로운 분기나 조건이 없다) 리뷰만으로 정확성을 확신할 수 있는 경우라고
보고 코드 레벨 검증으로 마무리했다.
