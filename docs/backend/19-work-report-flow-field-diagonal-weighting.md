# 작업 보고서 — Flow Field 대각선 가중치 수정 (몬스터 이동 경로 꺾임 버그)

> 유저가 스크린샷으로 보고한 "잡몹(trash) 이동 경로가 코어를 향해 완만한 대각선이 아니라
> 산봉우리 모양으로 꺾여 보인다" 버그를 진단하고 고쳤다. 고치는 과정에서 새 구현에
> 부동소수점 정밀도 버그가 하나, 그리고 이번 수정이 아니었으면 계속 가려져 있었을
> `moveMonster`의 잠재 버그가 하나 더 발견되어 함께 고쳤다.

---

## 1. 기획 — 무엇을, 왜

스크린샷 속 빨간 이동 경로는 화면 밖 좌상단에서 시작해 한 번 봉우리처럼 꺾인 뒤 코어로
내려오는 형태였다. `packages/shared/src/sim/ai/flowField.ts`를 보니 원인은 명확했다:
기존 구현이 8방향 이웃을 **전부 비용 1**로 취급하는 단순 BFS였다. 이러면 목표까지의
"최단 경로"가 유클리드 거리가 아니라 **체비셰프 거리** 기준으로 계산된다 — 대각선 한 칸과
직선 한 칸이 똑같이 취급되니, 실제 최단 경로는 "짧은 축을 먼저 대각선으로 따라잡고 긴
축은 나머지를 직선으로 마저 가는" 형태가 되어버린다. 장애물이 전혀 없는 개활지에서도
몬스터가 완만한 대각선이 아니라 꺾인 경로로 걷는 게 바로 이 때문이었다.

같은 대화에서 유저가 "플레이어 대각선 이동 시 x/y 축 속도가 상하좌우 이동과 같아서
부자연스럽다"는 것도 같이 봐달라고 했다. 이건 Playwright로 실제 이동 거리를 측정해
확인했는데(직선 이동 1000ms에 Δx=105, 대각선 이동 1000ms에 Δx=Δy=75), `normalizeMoveVector`
(`packages/shared/src/sim/movement.ts`)가 대각선 입력을 1/√2로 정확히 정규화하고 있어서
**버그가 아님**을 확인했다. 코드 변경 없이 이 부분은 넘어갔다.

## 2. 과정 — 어떻게 했나

### 2.1 가중치 다익스트라로 교체

`flowField.ts`의 거리 계산을 단순 BFS(정수 `Int32Array` 비용, FIFO 큐)에서 **가중치
다익스트라**(실수 `cost` 배열, 이진 최소 힙)로 바꿨다. 대각선 이동 비용은 √2, 직선은 1 —
실제 유클리드 거리에 맞는 가중치라 개활지에서는 사실상 직선에 가까운 경로가 나오고,
장애물을 우회하는 성질은 그대로 유지된다.

최소 힙(`MinHeap`)은 지연 삭제(lazy deletion) 방식으로 구현했다: 같은 셀이 더 낮은
비용으로 여러 번 큐에 들어갈 수 있고, `pop()` 시점에 "이미 그보다 낮은 비용으로 확정된
항목"이면 건너뛴다. decrease-key를 직접 구현하는 것보다 간단하고, 그리드 규모(최대
128×128)에서는 성능 차이가 없다.

### 2.2 겪은 문제 1 — Float32 반올림이 지연 삭제를 오작동시킴

구현 직후 테스트 5개 중 2개(`flowField.test.ts`), 그리고 이걸 쓰는
`world-combat.test.ts`의 군집 분리 테스트 1개가 실패했다. 증상은 "분명 도달 가능한
셀인데 `sampleDirection()`이 `{0,0}`을 돌려준다"는 것이었다.

디버그용 임시 테스트로 10×10 그리드의 비용 배열을 직접 찍어보니, 정답(브루트포스 완화로
계산한 값)보다 큰 값이 나오거나 아예 미도달(-1)로 남는 셀들이 있었다. 다익스트라 pop
순서를 로깅해서 원인을 찾았다:

```
STALE pop cost=1.4142135623730951 idx=44 actual=1.4142135381698608
```

`cost` 배열이 `Float32Array`였는데, 힙에 넣는 비용(`nCost`)은 배정밀도(double) 그대로다.
`this.cost[nIndex] = nCost`로 저장하는 순간 `Float32Array`가 값을 미세하게 반올림한다
(`Math.SQRT2` → `1.4142135623730951`이 `1.4142135381698608`로). 그 셀을 힙에서 꺼낼 때
지연 삭제 검사(`top.cost > this.cost[top.index]`)가 "원본(반올림 전) 값 > 반올림된 저장값"이
되어 **그 항목이 자기 자신보다 나쁘다고 오판해 최초의 정상 항목조차 건너뛰어버렸다**.
그 결과 해당 셀이 영영 확장되지 않아, 하류 셀들은 더 먼 우회 경로로만 도달하거나(과다
비용) 아예 도달 못 하는 셀도 생겼다(그리드 모서리).

고친 방법은 `cost` 배열을 `Float32Array`에서 `Float64Array`로 바꾼 것 — 힙의 비용과
정밀도를 맞추니 반올림 불일치가 사라졌다. (`dirX`/`dirY`는 방향 성분이라 정밀도가
중요하지 않아 `Float32Array`로 남겨둠.)

### 2.3 겪은 문제 2 — `moveMonster`의 정규화가 분리력 차이를 지워버림

Flow Field를 고치고 나니 `flowField.test.ts`는 전부 통과했지만,
`world-combat.test.ts`의 "가까이 겹친 몬스터끼리는 서로 밀어내서 간격이 벌어진다"
테스트가 여전히 실패했다(`gapAfter(10)`이 `initialGap(10)`보다 크지 않음 — 즉 두
몬스터가 전혀 안 벌어짐).

원인을 추적해보니 backend/17에서 만든 `moveMonster`가 주 이동 방향과 분리 벡터를
더한 뒤 **합을 단위 벡터로 정규화**하는 구조였다. 테스트 시나리오는 두 몬스터가
코어와 정확히 같은 축(y=0) 위에 있는 경우라, 분리력도 같은 축(x) 위에서만 작용한다.
이 경우 두 몬스터 모두 "주 방향(-1,0) + 분리(±0.36,0)"의 부호가 같아서, 정규화하면
결국 **둘 다 똑같이 (-1,0)** 이 되어버린다 — 분리력의 세기 차이(한쪽은 밀려서 더 세게,
반대쪽은 덜 세게)가 정규화 과정에서 완전히 지워지는 것이다.

이 버그는 이전엔 드러나지 않았는데, 예전 BFS 기반 Flow Field가 체비셰프 거리 아티팩트
때문에 정확히 수평은 아닌 살짝 비스듬한 방향을 돌려줬고, 그 우연한 비대칭 덕분에
정규화 후에도 두 몬스터의 이동 벡터가 미세하게 달라져 테스트가 우연히 통과하고
있었을 뿐이다. Flow Field를 수학적으로 올바르게 고치면서(축 위에서는 정확히 (±1,0))
이 잠재 버그가 그대로 드러났다.

고친 방법: 주 방향은 그 자체로 단위 벡터 정규화해 `speed`를 곱하고, 분리 벡터는
**합쳐서 다시 정규화하지 않고** 별도의 변위로 그 위에 더한다. 이러면 몬스터마다 실제로
받는 분리력 세기 차이가 이동 결과에 그대로 반영된다.

### 2.4 테스트

기존 5개 테스트(`flowField.test.ts`)와 82개 전체 스위트(`shared`)를 그대로 사용 —
새 테스트를 추가하진 않았다. 이번 수정은 기존에 있던 계약(대각선 우회, 도달 불가 처리,
군집 분리로 간격이 벌어짐 등)을 실제로 만족시키는 게 목적이라, 기존 테스트가 이미
정확한 회귀 기준이었다.

## 4. 다음 작업

- `SEPARATION_WEIGHT`(0.6) 등 분리 관련 상수는 여전히 임의값이다. `moveMonster`가
  이제 "주 방향(단위, `speed`) + 분리(가중치 적용, `speed` 배율)"를 그대로 더하는
  구조라, 여러 마리가 한 점에 몰리면 이론상 순간 속도가 `speed`보다 커질 수 있다 —
  지금까지 관찰된 시나리오에서는 문제가 없었지만, 실제로 몬스터가 몰리는 웨이브를
  본 뒤(클라이언트 렌더링) 필요하면 합산 벡터 길이를 `speed`로 상한 클램프하는 걸
  고려한다.
- Flow Field 재계산(`recompute`)은 지금도 건축물 설치/파괴 이벤트가 있을 때만 호출하는
  구조를 유지한다 — 이번 수정은 계산 정확도만 바꿨고 호출 빈도/캐싱 전략은 그대로다.
