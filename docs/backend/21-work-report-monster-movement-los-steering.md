# 작업 보고서 — 몬스터 이동 자연스럽게 만들기(시야선 직진 + Flow Field 우회 병행)

> backend/19에서 Flow Field 대각선 가중치를 고쳤는데도, 몬스터 경로가 스크린샷에서
> 여전히 "상하좌우/대각선 8방향으로만 걷다가 코어 근처에서 축 정렬로 꺾이는" 모습이라는
> 피드백을 받았다. 원인을 실측으로 확인하고, 두 단계로 고쳤다.

---

## 1. 기획 — 무엇을, 왜

사용자가 스크린샷으로 보여준 증상: 몬스터가 스폰 지점에서 코어까지 거의 직선으로 오다가,
코어 근처에서 상하좌우 중 하나로 갑자기 꺾여 들어온다. backend/19에서 대각선 이동
비용을 정확히(√2) 고쳤는데도 왜 이런 모습이 남았는지부터 확인해야 했다.

## 2. 과정 — 어떻게 했나

### 2.1 원인 재확인 — 옥타일 거리 필드는 근본적으로 그라디언트가 유한하다

디버그 스크립트로 실제 방향 벡터를 각도로 찍어보니, 경로가 특정 몇 개 각도
(0°, 22.5°, 45°, 67.5°, 90°...)에서만 딱딱 끊기는 걸 확인했다. 이건 backend/19에서 고친
"8방향 이웃 중 최저 비용 하나를 그대로 방향으로 쓰는" 방식의 한계였다 — 셀마다 방향이
반드시 8가지 값 중 하나로 양자화된다.

먼저 방향 계산을 **비용 필드의 그라디언트(중앙차분)** 로 바꿨다. 다익스트라 비용이
이제 실제 가중 유클리드 거리에 가깝기 때문에, 그 필드를 미분하면 이론적으로 더 정교한
방향이 나올 거라 기대했다 — 실제로 8방향에서 16방향으로 늘었고, 이웃 4개(상하좌우)만
보면 되니 계산도 더 쌌다(§flowField.ts).

그런데 다시 각도를 찍어보니 여전히 유한한 각도(0/22.5/45/67.5/90°...)로만 끊겼다.
이유를 따져보니 **옥타일 거리 자체가 수학적으로 구간별 선형(piecewise linear) 함수라
그라디언트가 구간마다 상수**다 — 방향 계산 방식을 아무리 다듬어도(스텝-최적 이웃
선택이든, 필드 그라디언트든) 격자 위에서 8방향 가중치로 만든 거리 함수의 미분값 자체가
유한한 각도 집합 밖으로 못 나간다. Flow Field 알고리즘의 근본적인 한계였다.

### 2.2 진짜 해결책 — 장애물이 없으면 코어로 직진, 있을 때만 Flow Field로 우회

지금 게임엔 건축물 시스템이 아직 없어서(docs/backend/18은 제안서 단계) `isBlocked`가
항상 `false`다 — 즉 Flow Field가 실제로 피해야 할 장애물이 하나도 없는 상태에서,
순전히 "격자라서 생기는 각도 제한" 때문에 부자연스러운 경로가 나오고 있었다.

해결 방법은: **목표(코어)까지 시야가 막힌 셀이 없으면, Flow Field 대신 목표를 향한
진짜 연속각(직선)으로 직진시킨다. 실제로 막힌 셀이 있을 때만 Flow Field 방향으로
우회한다.** 장애물이 없는 지금 상태에선 사실상 항상 직진이 되어 스크린샷 문제가
완전히 사라지고, 나중에 건축물이 생기면 그 건물을 가로막는 몬스터만 자동으로 Flow
Field 우회 경로를 타게 된다 — Flow Field 인프라(다익스트라 거리맵, 그라디언트 방향)는
그대로 남겨두고 "장애물이 실제로 있을 때"의 폴백으로만 쓰는 구조다.

구현(`packages/shared/src/sim/ai/flowField.ts`):

- `FlowField.hasLineOfSight(fromX, fromY, toX, toY)`: 두 월드 좌표 사이에 막힌 셀이
  있으면 false. 반 타일 간격으로 선분을 샘플링해서 지나치는 셀을 확인한다 — 완벽한
  격자 순회(DDA)보다 구현이 단순하고, 반 타일보다 촘촘하니 어떤 셀도 통째로 건너뛰지
  않는다(선분이 셀 모서리를 아주 살짝 스치기만 하는 극단적인 경우는 놓칠 수 있는데,
  실시간 게임에서는 무시할 만한 오차로 판단했다).
- `hasObstacles` 플래그: `recompute()`가 그리드 전체를 한 번 훑어서 막힌 셀이 하나라도
  있는지 캐싱해 둔다. 지금처럼 건축물이 전혀 없으면 `hasLineOfSight`가 순회 자체를
  생략해서(early return true) 사실상 공짜다. `recompute()`는 건축물 설치/파괴 같은
  드문 이벤트에만 불리니 이 스캔 비용도 무시할 수준이다.
- `world.ts`의 `tickMonsters()`: 코어를 향해 걷는 분기(타겟 없음)에서
  `flowField.hasLineOfSight(monster.x, monster.y, 0, 0)`을 먼저 확인하고, 시야가
  열려 있으면 `normalize(-monster.x, -monster.y)`(코어를 향한 연속각)로 직진, 막혀
  있으면 기존처럼 `flowField.sampleDirection()`(그라디언트 방향, 우회용)을 쓴다.

### 2.3 테스트

`flowField.test.ts`에 `hasLineOfSight` describe 블록 3개 추가:
- 장애물이 하나도 없으면 항상 true
- 두 점 사이를 가로지르는 막힌 셀이 있으면 false
- 막힌 셀이 있어도 그 셀을 지나지 않는 경로면 true

World 레벨에서 실제 건축물로 장애물을 만들어 우회 여부를 검증하는 통합 테스트는
추가하지 않았다 — 지금 `World`는 `FlowField`를 항상 기본(장애물 없음) 설정으로만
생성해서, 건축물 시스템이 실제로 붙기 전엔 World에 장애물을 주입할 방법 자체가 없다
(docs/backend/18 제안서 단계). `FlowField` 단위 테스트로 우회 로직 자체는 이미
검증했다.

## 4. 다음 작업

- 건축물 시스템이 실제로 붙으면(docs/backend/18) `World`가 `FlowField`에 실제
  `isBlocked` 콜백을 넘기게 될 텐데, 그때 `hasLineOfSight` 기반 우회 전환이 실제로
  발동하는지 통합 테스트로 확인이 필요하다.
- `hasLineOfSight`의 반 타일 샘플링은 선분이 셀 모서리를 스치기만 하는 극단적인
  경우를 놓칠 수 있다(§2.2). 건축물이 생겨서 실제로 문제가 되면(예: 몬스터가 벽
  모서리를 살짝 통과) 샘플 간격을 좁히거나 정식 DDA로 바꾸는 걸 고려한다 — 지금은
  장애물이 없어 검증할 수도 없는 가상의 시나리오라 미리 손대지 않았다.
- 어그로 추격 중(타겟이 있는 분기)은 원래부터 항상 타겟을 향한 직선(연속각)이라 이번
  변경과 무관하다. Flow Field/시야선 로직은 "타겟 없이 코어로 향할 때"에만 관여한다.
