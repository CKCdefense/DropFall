# 제안서 — 자원채집·건축 MVP 범위

> [backend/11](11-mvp-scope-proposal-combat-wave.md)과 같은 방식으로, 코드 구현 전에
> 기획서에 없는 세부 범위를 먼저 정리한다. **아직 코드 구현은 하지 않았다.**
> 원래 로드맵상 `building.ts`는 역할 B(게임플레이) 담당이지만, 압축 일정상 combat/wave를
> A가 먼저 만든 것과 같은 흐름으로 이번에도 A가 먼저 손댄다 — 팀 내 B 작업과 겹치는지
> 먼저 확인할 것.

## 1. 이미 문서에 정해져 있어서 그대로 따르는 것

| 항목 | 내용 | 출처 |
|---|---|---|
| 그리드 2레이어 | `blocksMovement`(이동 차단) / `blocksProjectile`(투사체 차단) 분리 | 기술명세 §5.2 |
| Flow Field 재계산 시점 | 건축물 설치/파괴 이벤트 시에만(매 틱 금지) | 기술명세 §5.1 |
| 울타리 | 내구도 낮음, 투사체 **통과**(뒤에서 사격 가능), 이동은 차단 | 기획서 §7.1 |
| 벽 | 내구도 높음, 투사체 **차단**, 이동도 차단 | 기획서 §7.1 |

| 건축 조작 | `B` 건축모드 토글, 좌클릭 설치·우클릭 취소, 그리드 스냅 | 기획서 §4 |
| 자원 원안 | 목재, 광물(희소)에너지결정·경험치 | 기획서 §6.3 |

## 2. 이번 요청으로 좁히는 범위

기획서 원안(자원 5종, 방어설비 5종)보다 훨씬 좁게 시작한다 — 로드맵 P0("기본 건축(벽/울타리)")
과도 정확히 일치한다.

| 원래 기획 | 이번 MVP | 비고 |
|---|---|---|
| 자원 5종 | **나무 · 돌 2종만** | 섬유/광물/반도체/에너지결정/경험치는 제외. "광물"을 "돌"로 단순화한 것으로 봄 |
| 방어설비 5종 | **벽 · 울타리 2종만** | 문/자동포탑/스파이크는 제외 |
| 도끼(근접무기 겸용) | **채집 전용 도구로 사용** | 전투 겸용 여부는 §4에서 확인 필요 |
| (기획서에 없음) | **곡괭이 신규 도입** | 돌 채집용. 기획서 원안엔 없던 아이템 — 도끼처럼 무기 겸용으로 할지 순수 도구로 할지 결정 필요 |

## 3. 새로 정해야 하는 것 — 제안값

기획서/기술명세에 수치·메커니즘이 없는 부분이다. 아래는 **구현을 시작하기 위한
플레이스홀더**이며, `shared/data/*.json`에 넣어 나중에 코드 수정 없이 조정한다
(기획서 §10 밸런싱 원칙 1).

### 3.1 채집 메커니즘

**제안**: `E`(상호작용 키, 기획서 §4에 이미 배정됨)를 자원 노드 앞에서 누르고 있으면
채집이 진행된다(채널링 방식) — 몽둥이 스윙처럼 즉발이 아니라, 홀드 중 일정 주기로
자원을 획득. 도구가 없으면 채집 자체가 안 되는 것으로 제안(맨손 채집 불가) — Minecraft류의
"맞는 도구 필요" 방식과 동일.

| 항목 | 값 |
|---|---|
| 나무 채집 판정 거리 | 32px (플레이어 근접) |
| 도끼 없이 나무 채집 | 불가 |
| 곡괭이 없이 돌 채집 | 불가 |
| 채집 주기 | 1초당 1회 |
| 회당 획득량 | 나무 5 / 돌 3 (돌이 더 귀함) |
| 노드 재생(리젠) 시간 | 나무 60초 / 돌 90초 |
| 노드 총 채집 가능 횟수(고갈 전) | 나무 5회 / 돌 3회 — 고갈되면 재생 시간 후 부활 |

### 3.2 도구

| 도구 | 대상 자원 | 전투 겸용 여부 |
|---|---|---|
| 도끼 | 나무 | **제안: 겸용**(기획서 §7.2 원안 그대로 — 근접무기 damage/fireRate는 backend/11의 몽둥이와 별개로 정의) |
| 곡괭이 | 돌 | **제안: 순수 도구**(전투 데미지 없음 또는 아주 낮은 보조 데미지만) |

> **미확정**: 도끼/곡괭이를 처음부터 소지한 채 시작할지, 상점에서 구매해야 할지.
> 상점 시스템 자체가 아직 없으므로 **이번 MVP는 전원 시작부터 소지**로 제안.

### 3.3 인벤토리(자원 보유)

**제안**: 팀 공유가 아니라 **개인별 보유**(기획서 §6.3 자원 획득 방식이 몬스터 경험치는
개인 획득이라고 명시한 것과 일관성 유지 목적). 건축 시에는 **설치를 실행한 플레이어의
인벤토리**에서만 자원을 차감한다(팀원 자원을 모아서 낼 방법은 이번 범위 밖).

| 항목 | 값 |
|---|---|
| 최대 보유량 | 나무 99 / 돌 99 (넉넉하게, 상한 자체보다 "부족하게 주는" 쪽으로 밸런스 — 기획서 §10 원칙 5) |

### 3.4 건축물 스탯 · 비용

| 건축물 | 나무 비용 | 돌 비용 | HP | blocksMovement | blocksProjectile |
|---|---|---|---|---|---|
| 울타리 | 5 | 0 | 50 | O | X |
| 벽 | 5 | 10 | 200 | O | O |

### 3.5 배치 규칙

- `TILE_SIZE`(16px) 그리드에 스냅, 1타일 = 건축물 1개 (기존 `constants.ts`의 `TILE_SIZE` 재사용)
- 배치 불가 조건: 이미 다른 건축물/자원 노드/코어가 있는 타일, 플레이어가 서 있는 타일
- 파괴: 몬스터 공격으로 HP 0 → 제거. 플레이어가 직접 철거하는 기능은 이번 범위 밖(설치만)

## 4. 팀/사용자 확인이 필요한 질문

- [ ] 도끼를 "전투 겸용"으로 둘지, 채집 전용으로 단순화할지 — backend/11에서 이미
      몽둥이를 근접무기로 확정해뒀어서, 도끼까지 겸용하면 근접무기가 2종이 된다
- [ ] 곡괭이도 전투에 쓸 수 있게 할지(약한 보조 데미지) 아니면 순수 도구로만 둘지
- [ ] 도구를 처음부터 소지 상태로 시작하는 것에 이견 없는지(상점 미구현 상태 임시 조치)
- [ ] 자원 노드를 맵에 몇 개, 어디에 배치할지 — 아직 맵 자체가 플레이스홀더 격자라
      "코어에서 일정 거리 이상 떨어진 곳에 N개 무작위 배치" 정도로 우선 제안
- [ ] 밤에도 채집 가능한지 — 기획서 §3.3은 "에너지 결정은 밤에도 주우러 나가야 한다"고
      하지만 이건 몬스터 드랍템 얘기다. 나무/돌 노드 자체를 밤에도 캘 수 있게 할지는
      미정 (제안: 가능하게 두되, 밤엔 몬스터가 있어서 위험을 감수해야 하는 정도로 자연히
      난이도가 생김 — 별도 제약 코드는 안 넣는 방향)

## 5. 합의되면 진행할 서버(역할 A) 하위 작업 순서

1. `shared/data/resources.json`(나무/돌 노드 스탯) / `tools.json`(도끼/곡괭이) /
   `buildings.json`(벽/울타리) + zod 스키마 로더
2. `shared/sim/building.ts` — 그리드 점유 맵(2레이어), 배치 유효성 검사, 건축물 HP/파괴
3. `shared/sim/world.ts`에 자원 노드 엔티티(위치/잔여 채집 횟수/재생 타이머) 추가
4. 인벤토리(플레이어별 나무/돌 보유량) — `PlayerEntity`에 필드 추가
5. `world.ts`에 채집 처리(`harvest(playerId)` — E 홀드 채널링) + 건축 처리
   (`placeBuilding(playerId, type, cx, cy)`) 연결
6. 몬스터가 건축물을 공격하도록 `tickMonsters()` 확장 — 지금은 "코어 아니면 플레이어"만
   공격 대상이라, 그 사이에 건축물이 끼는 경우(막힘 감지, 기술명세 §5.3) 추가 필요
7. 건축물 설치/파괴 시 `FlowField.recompute()` 트리거 연결 — 지금은 `World` 생성 시
   1회만 계산하는데, 이제부터 이벤트 기반으로 실제로 다시 계산해야 한다
8. `shared/protocol/messages.ts`에 `HarvestInputMessage`/`BuildInputMessage` 추가(+타입 검증)
9. 서버: `GameRoomState`/`GameRoom`에 자원 노드·건축물·인벤토리 동기화 연결
10. Vitest 테스트 + `pnpm lint`/`typecheck`/`build` 전체 검증
