# 작업 보고서 — 플레이어 충돌 반경 디버그 테두리(C 토글)

> backend/28에서 만든 플레이어-건축물 하드 충돌은 원형 판정이라 실제 반경이 얼마인지
> 코드를 안 보면 알 수 없다. 도형 플레이스홀더일 땐 몸통 크기와 판정 범위가 어느 정도
> 비슷해 보였지만, 실제 캐릭터 스프라이트를 씌우고 나니 그림만 봐서는 판정 범위를
> 가늠할 수 없게 됐다 — 확인용으로 C 키 토글 디버그 테두리를 추가했다. 처음엔 플레이어
> 위에 "합산 반경" 원 하나만 그렸는데, 사용자가 직접 써보고 "직관적이지 않고 막히는
> 범위를 제대로 표현 못 한다"고 지적해서 — 플레이어 원 + 건축물 원, 두 개로 나눠
> 그리는 방식으로 다시 만들었다.

---

## 1. 기획 — 무엇을, 왜

"캐릭터 에셋 입혀서 실제 범위를 알기 힘드니 테두리 씌워서 확인할 수 있게 해달라"는
요청. 핵심은 **눈에 보이는 원이 시뮬레이션이 실제로 쓰는 값과 한 치도 어긋나면
안 된다**는 것 — 디버그 표시가 실제 판정과 다르면 오히려 잘못된 감각을 심어준다.

## 2. 과정 — 어떻게 했나

### 2.1 1차 시도 — 플레이어 위에 합산 반경 원 하나

`isBlockedForPlayer`가 실제로 쓰는 `PLAYER_BUILDING_COLLISION_RADIUS`(플레이어 자신의
반경 `HIT_RADIUS` + 건축물 자신의 반경 `TILE_SIZE/2`의 합, backend/28)를 그대로
export해서, 플레이어 위에 그 반경만큼의 원을 하나 그렸다. 값 자체는 정확했지만,
사용자 피드백: "직관적이지 않고 막히는 캐릭터 범위를 제대로 표현하지도 못하는 것
같다." 원인을 되짚어 보니 — 이 원은 플레이어 혼자만의 크기가 아니라 **건축물의
반경까지 미리 얹어서 부풀린 값**이라, 원의 가장자리가 건축물의 실제 가장자리와
시각적으로 아무 관계가 없어 보인다. "이 원이 건물에 닿으면 막힌다"가 아니라 그냥
"플레이어가 이상하게 크게 그려진다"로 읽힌 것.

### 2.2 2차 시도 — 플레이어 원 + 건축물 원으로 분리

원-원 충돌은 "두 반경의 합보다 중심 간 거리가 가까우면 겹친다"는 규칙이다. 즉
`PLAYER_BUILDING_COLLISION_RADIUS` 자체가 "두 원이 맞닿는 지점"을 뜻한다. 이걸
그대로 반영해서, **플레이어에는 플레이어 자신의 반경(`HIT_RADIUS`, 10px)을, 각
건축물에는 건축물 자신의 반경(`TILE_SIZE/2`, 8px)을 각각 따로 그렸다.** 이제
"두 원의 가장자리가 맞닿는 순간이 곧 막히는 지점"이라는 걸 그대로 눈으로 볼 수
있다 — 사용자가 벽/울타리 쪽으로 다가가면서 두 원이 가까워지다가 맞닿는 걸 직접
보고 "여기서 막히겠구나"를 예측할 수 있다. 색도 구분했다(플레이어는 하늘색, 건축물은
기존 노란색).

이동을 막지 않는 건축물이 생기면(지금은 전부 `blocksMovement: true`라 해당 없음)
그 건축물에는 원을 안 그리도록 `buildingsData[building.type]?.blocksMovement` 조건을
같이 넣었다 — 안 막는 건축물에 원을 그리면 "여기도 막힌다"는 반대의 오해를 준다.

### 2.3 값 export

`HIT_RADIUS`(combat.ts)와 `TILE_SIZE`(constants.ts)는 이미 서버/시뮬레이션이 쓰는
바로 그 값이고, 둘 다 `@dropfall/shared`에서 그대로 가져올 수 있게 재수출했다 —
클라이언트에 반경을 따로 하드코딩하면 나중에 밸런스 조정으로 값이 바뀔 때 조용히
어긋날 위험이 있어서 피했다.

### 2.4 렌더링 — `EntityRenderer`

`createPlayer()`/`createBuilding()` 각각에 스트로크만 있고 채움은 없는 원
(`collisionDebug`)을 하나씩 추가했다. 컨테이너 원점(0,0)이 곧 서버 좌표이므로,
스프라이트 origin 오프셋과 무관하게 반경만 맞추면 실제 판정 범위와 그대로 겹친다.
기본은 `visible=false`, `setCollisionDebugVisible(visible)`로 플레이어·건축물
양쪽 전체를 한 번에 켜고 끈다.

### 2.5 토글 — C 키

`GameScene.create()`에서 `C` 키에 토글 리스너를 달았다. 기존 키(WASD, E=채집,
V=낮 넘기기 투표, B=건축모드)와 안 겹치는 여유 키를 골랐다. 상시 켜두면 실제 플레이
화면이 지저분해지므로, 필요할 때만 눌러서 확인하는 디버그 전용 기능으로 남겼다.

### 2.6 검증

`pnpm --filter client dev`로 띄운 뒤 Playwright로 "오프라인으로 혼자 해보기"에
진입해 실제로 확인했다:

1. C를 누르면 플레이어에 하늘색 원, 건축물(울타리)에 노란 원이 각각 뜨고, 다시
   누르면 둘 다 사라진다.
2. 나무를 채집해 울타리를 지은 뒤, 플레이어를 울타리 쪽으로 이동시키면서 두 원이
   서서히 가까워지다 맞닿는 지점에서 실제로 이동이 멈추는지 확인했다 — 맞닿기 전엔
   `d`를 눌렀을 때 프레임당 정상 이동량만큼 좌표가 늘었고, 원이 맞닿은 뒤로는 `d`를
   0.8초 더 눌러도(원래대로면 80px 더 이동해야 함) 좌표가 **완전히 고정**됐다.
   (처음 시도에서는 마우스 클릭으로 건축물을 놓을 때 플레이어와 같은 행(row)에
   정확히 놓이지 않아 두 원이 계속 어긋나 보였는데 — 이건 수동 클릭 배치의 오차였고
   실제 충돌 로직 문제가 아니었다. 같은 행에 정확히 놓고 나서 재현했다.)

```bash
pnpm --filter @dropfall/shared test     # 128 passed(export만 늘었을 뿐 로직 변경 없음), 안정
pnpm typecheck                          # client/server 전체 통과
pnpm lint                               # 에러 0
pnpm build                              # client(vite)/server(tsup) 전체 통과
```

전부 통과.

## 3. 결과

- 플레이어 자신의 반경(10px)과 건축물 자신의 반경(8px)을 각각 따로 확인할 수 있고,
  두 원이 맞닿는 지점이 곧 실제 충돌 지점과 정확히 일치한다 — 합산 반경 하나짜리
  원보다 훨씬 직관적이다.
- 반경 값은 `HIT_RADIUS`/`TILE_SIZE` 두 개뿐이라, 나중에 밸런스 조정으로 값이
  바뀌어도 디버그 테두리가 자동으로 따라간다(재조정 불필요).
