# 작업 보고서 — 몬스터 콜로니(협동 강제) + 스폰 위치 조정

> 해커톤 심사 포인트로 "협동 요소"를 강화하기로 하고, 낮 시간까지 위협이 존재하는
> 몬스터 콜로니와 그걸 부수는 채널링(엄호 필요) 메커니즘을 새로 만들었다. 동시에
> 몬스터 스폰 반경을 맵 가장자리로 옮겨 "몰려온다"는 느낌을 살렸다.
>
> **[추가 반영]** 초기 구현 후 "채널링(제거 작업) 중인 콜로니는 스폰도 멈춰야
> 한다"는 후속 요청을 받아 반영했다 — §2.2 끝부분 참고.

---

## 1. 기획 — 무엇을, 왜

지금까지 나온 협동 요소(자원 공유 풀, 코어 상호작용 모달)는 "하면 좋은" 수준이지,
인원을 강제로 나누게 만드는 요소는 없었다. 사용자가 두 가지를 제안했다:

1. **몬스터 콜로니** — 맵 4방향에 고정 배치된 구조물. 낮에도 주기적으로 몬스터를
   내보내서, 낮이 "무조건 안전한 채집 시간"이 아니라 채집 인원과 방어 인원을 나눠야
   하는 압박이 되게 한다. 콜로니를 부수려면 한 명이 채널링(폭탄 설치 등) 동안
   무방비해지고, 그 사이 다른 인원이 엄호해야 한다.
2. **스폰 위치 조정** — 몬스터가 코어 바로 근처(300px, 맵 반폭 1024px 중 극히
   일부)에서 생겨나던 걸 가장자리 쪽으로 옮긴다.

설계 논의에서 확정한 5가지: (1) 콜로니는 웨이브가 진행될수록 마릿수/종류가
늘어난다, (2) 채널링은 피격 또는 이동 시 중단된다, (3) 채널 1회 완료 = 파괴(밸런스
단계에서 바뀔 수 있음), (4) 파괴 보상은 코어 업그레이드/상점 전용 새 자원("에너지"
— 마침 frontend/09의 `CoreModal`에 이미 플레이스홀더 행으로 있었다), (5) 콜로니와
밤 웨이브 스폰은 완전히 독립(서로 얽지 않는다).

## 2. 과정 — 어떻게 했나

### 2.1 기존 구조 확인 — 생각보다 손댈 곳이 적었다

- `World.tickMonsters()`는 페이즈(낮/밤)와 무관하게 매 틱 `this.monsters`를 그냥
  순회한다. 낮에 몬스터가 없던 건 `WaveManager`가 낮엔 스폰을 안 시켜서일 뿐 —
  콜로니가 낮에 몬스터를 추가해도 추격/공격/피격 로직은 그대로 재사용된다.
- `FlowField.sampleDirection`은 그리드 밖 좌표에서 `{0,0}`을 돌려주는데,
  `tickMonsters()`엔 이미 "방향을 못 구하면 코어로 직진"하는 폴백(backend/27,
  코어를 벽으로 완전히 둘러싼 경우 대비)이 있다. 이 폴백이 그리드 밖에서 스폰된
  몬스터에도 그대로 먹혀서, 콜로니를 맵 경계 훨씬 밖에 놔도 FlowField 쪽은 전혀
  손댈 필요가 없었다.

### 2.2 데이터/시뮬레이션

- `waves.json`의 `spawnRadius`를 300 → 900으로(맵 반폭 1024px 중 124px 여유).
- `colonies.json`(신규) + `data/index.ts`의 `ColoniesDataSchema` — 채널 시간,
  파괴 보상량, 그리고 "웨이브 진행도별 스폰 주기/몬스터 종류" 스테이지 배열.
  밤 웨이브(`waves.json`)가 이미 웨이브 번호로 난이도 곡선을 그리는 것과 같은 축을
  재사용해서, "시간이 지날수록"을 게임 내 절대 초가 아니라 웨이브 진행도로 표현했다.
- `sim/colony.ts`(신규) — `BuildingRegistry`(building.ts)와 같은 위상의
  `ColonyRegistry`. 코어 중심 N/E/S/W 고정 위치에 4개 생성한다. 밤 웨이브 스폰
  지점(`buildSpawnPoints`)과 달리 **판마다 회전하지 않는다** — "동쪽 콜로니"처럼
  방향으로 기억하고 매판 다시 찾아가야 하는 랜드마크이기 때문이다. 파괴돼도
  엔티티는 지우지 않고 `destroyed` 플래그만 켠다(위치가 계속 의미가 있다).
- `World`에 `tickColonies()`(스폰) + `tickChannels()`(채널링 진행) 추가.
  - **채널링 상태 판정**: 매 틱 플레이어의 최신 입력에서 `channeling === true`
    이고 `moveX === 0 && moveY === 0`이고 파괴 안 된 콜로니가 사거리 안에 있고
    이번 틱에 피격당하지 않았으면 진행률이 오른다. 조건이 하나라도 깨지면 그
    자리에서 0으로 리셋 — 부분 진행을 이어서 채우는 게 아니라 매번 처음부터
    다시 시작해야 한다(이게 "엄호"를 실제로 필요하게 만드는 핵심 규칙).
  - **피격 판정 인프라**: 플레이어 hp를 깎던 세 곳(몬스터 추격 공격, 보스 돌진,
    보스 광역)을 새 `damagePlayer()` 헬퍼로 통합하고, 그 안에서
    `tookDamageThisTick` 플래그도 같이 세팅했다. `tickChannels()`는
    `tickMonsters()` 다음에 불러서 이번 틱의 피격이 이미 반영된 뒤에 판정한다.
  - **입력 프로토콜**: `PlayerInputMessage`에 `channeling?: boolean` 추가.
    moveX/moveY/aimAngle과 같은 "누르고 있는 동안 매 틱 재전송" 모델에 자연스럽게
    맞아서 새 메시지 타입을 만들지 않았다. 옵셔널로 둬서 기존 테스트/호출부가
    이 필드 없이 보내도 그냥 false로 취급되게 했다(전부 다시 고칠 필요 없음).
  - `fireWeapon()`에 `if (player.channelingColonyId) return;` 추가 — 채널링
    중엔 공격 자체가 안 나간다. "무방비 상태"를 실제로 강제하는 부분.
  - **[추가 반영] 채널링 중인 콜로니는 스폰도 완전히 멈춘다.** 처음엔 스폰과
    채널링을 서로 무관한 시스템으로 뒀는데, 사용자가 "제거 작업 중일 때는
    콜로니에서 몬스터 생성도 멈춰야겠다"고 제안했다 — 채널링 중에도 계속
    몬스터가 나오면 엄호 인원이 더 불리해지기만 하고, "채널링을 시작했다"는
    행위 자체의 의미도 흐려진다. `tickColonies()`에서 해당 콜로니를 채널링
    중인 플레이어가 있으면(`isColonyBeingChanneled()`) 스폰뿐 아니라
    **스폰 타이머 자체를 얼린다**(감소시키지 않음) — 그냥 스폰만 건너뛰고
    타이머는 계속 줄이면, 채널링이 중간에 끊겼을 때 밀린 스폰이 한꺼번에
    터져나오는 부자연스러운 결과가 되기 때문이다. 이걸 같은 틱 안에서
    정확히 반영하려면 `tick()` 안에서 `tickChannels()`(채널 상태 갱신)가
    `tickColonies()`(스폰 판정)보다 먼저 불려야 한다 — 순서를 바꿨다.

### 2.3 서버/클라이언트 동기화

- `GameRoomState`에 `ColonySchema`(x/y/destroyed), `coreSharedEnergy`,
  `PlayerSchema.channelProgress` 추가. `GameRoom`에 `syncColonies()` 추가 —
  콜로니는 4개 고정이고 절대 사라지지 않아서(파괴돼도 destroyed만 바뀜) 몬스터처럼
  "죽은 id 지우기" 루프가 필요 없다.
- `GameConnection`/`ColyseusConnection`/`LocalConnection`/`SnapshotInterpolator`에
  `ColonyView`/`coreSharedEnergy`/`channelProgress` 배관 — 기존 `resourceNodes`/
  `buildings` 패턴을 그대로 따라했다. 콜로니는 위치가 고정이라 보간 대상에서
  빼고(건축물과 동일하게) 최신값을 그대로 쓴다.

### 2.4 클라이언트 입력/렌더

- `InputController`에 채널 키(R) 추가 — moveX/moveY와 같은 자리에서
  `channeling: keys.channel.isDown`을 매 입력에 실어 보낸다.
- `EntityRenderer`에 콜로니 플레이스홀더(보라색 사각형, 파괴되면 흐리게) 추가.
- **미니맵 사거리 문제를 발견해서 같이 고쳤다**: `Minimap.ts`의 `WORLD_RANGE`가
  420px이었는데, 콜로니는 900px 밖에 있어서 이대로 두면 미니맵에 아예 안 잡혀
  방향을 찾을 방법이 없었다. 950px로 올렸다(이번 작업이 실제로 플레이 가능하려면
  꼭 필요한 수정이라 범위 밖으로 미루지 않았다).
- `CoreModal`의 "에너지" 플레이스홀더 행을 실제 `coreSharedEnergy`에 연결했다 —
  frontend/09가 만들어 둔 모달 중 처음으로 실데이터가 들어간 필드다.
- HUD에 자기 채널 진행률(`콜로니 파괴 중... NN%`) 텍스트, 조작 힌트에 `[R]` 추가.

## 3. 결과 — 검증

```bash
pnpm --filter @dropfall/shared test   # 16 files, 221 tests 전부 통과(신규 15개 포함)
pnpm typecheck                        # client/server 전체 통과
pnpm lint                             # 에러 0
pnpm build                            # client(vite)/server(tsup) 전체 통과
```

`packages/shared/tests/colony.test.ts`(신규)에서 검증한 것: 4개 고정 배치, 낮에도
스폰됨, 파괴된 콜로니는 스폰 중단, 진행률 증가, 완료 시 파괴+에너지 지급, 사거리
밖에서는 시작 안 됨, 이동/피격/채널키 뗌 각각으로 리셋됨, 파괴된 콜로니는 채널링
자체가 안 됨, 채널링 중 공격 불가, **채널링 중인 콜로니는 스폰 경계가 와도
몬스터가 안 나오고 타이머가 얼어붙음**, **채널이 끊기면(파괴는 안 된 채) 얼어있던
타이머가 다시 흘러 밀린 스폰이 바로 일어남**. `colonyStageFor()`는 별도로 순수
함수 단위 테스트로 "afterWave 경계"와 "스테이지가 올라갈수록 더 강해진다
(주기↓·종류↑)"는 성질을 데이터 값과 무관하게 검증했다.

Playwright로 실제 화면 확인은 이번엔 생략했다 — "엄호" 상황 자체가 2인 이상 필요한
시나리오라 로컬 단일 클라이언트로 재현하기 어렵고, 핵심 로직(스폰/채널/중단/파괴)은
위 유닛 테스트가 이미 상세히 다룬다.

## 4. 다음 작업

- **에너지 소비처 미구현** — `UpgradeModal`/`StoreModal`이 아직 실제 데이터에
  연결되지 않았다(frontend/09 자체가 선작업 단계). 상점/업그레이드 콘텐츠가
  설계되면 `coreSharedEnergy`를 소비하는 실제 로직을 붙여야 한다.
- **콜로니 파괴가 밤 웨이브 스폰 지점에 영향을 주지 않음** — 사용자가 명시적으로
  "완전히 독립"으로 확정했지만, 나중에 "콜로니를 부술수록 밤도 편해진다"는 추가
  보상을 원하면 `WaveManager`가 콜로니 상태를 참조하도록 별도 작업이 필요하다.
- **콜로니 월드 진행률 표시 없음** — 지금은 채널링하는 본인만 HUD 텍스트로 진행률을
  본다. 엄호하는 동료가 "얼마나 남았는지" 보려면 콜로니 위에 진행률 링 같은 걸
  그려야 하는데, 이번엔 스코프 아웃했다.
- **밸런스 값 전부 임의값** — `channelSeconds`(6), `essenceReward`(1),
  `stages`의 주기/종류, `spawnRadius`(900) 전부 플레이테스트 후 조정이 필요하다.
  특히 `spawnRadius`를 3배로 올리면서 몬스터 이동 거리도 3배가 됐는데,
  `waves.json`의 `nightDuration`은 이번엔 건드리지 않았다 — 실제로 플레이해보고
  너무 늘어지면 같이 조정할 것.
- **지형 확장 필요할 수 있음** — 지형(`terrain/`) 타일이 확장된 스폰 반경/콜로니
  위치까지 실제로 덮여 있는지는 확인하지 않았다(클라이언트 지형 담당 C 영역).
  콜로니/몬스터가 맨 배경 위에 보이면 별도로 전달할 것.
