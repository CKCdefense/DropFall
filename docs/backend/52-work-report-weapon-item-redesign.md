# 52. 무기·아이템 전면 재설계 (작업 보고)

기존 13종(권총/매그넘/소총/산탄총/미니건/빔소드 + 도구 7종)을 걷어내고, 티어가 있는
**근접 7종 + 원거리 12종**과 **치료 5종 + 음식 6종**으로 갈아엎었다. 에셋도 새 팩
(`weapons_new.aseprite`, `item_usable.aseprite`)으로 교체했다.

## 1. 무엇이 새로 생겼나

기존 시스템에는 없던 규칙들이 이번에 들어왔다.

| 기능 | 어디에 |
|---|---|
| 탄창·재장전 | `WeaponAmmo` (sim/combat.ts) |
| 산탄(펠릿 여러 발) | `resolveFire`가 배열을 반환 |
| 관통 | `ProjectileEntity.pierce` + `hitIds` |
| 점사 모드 | `World.bursts` + `toggleFireMode` |
| 소모품 버프(진통제·아드레날린) | `PlayerEntity.hpFloorTimer` / `speedBuffTimer` |
| 음식 영구 스탯 | `maxHpBonus` / `attackBonus` / `staminaBonus` |
| 채집 효율 분리 | `weapons.json`의 `gatherMultiplier` |
| 무기별 사거리 | `weapons.json`의 `maxRange` |
| 야간 조명 | `weapons.json`의 `lightRadius` (클라 연출 전용) |

`magazine`/`reloadTime`은 예전부터 데이터에만 있고 아무도 읽지 않는 **죽은 필드**였다.
이번에 실제로 쓰이게 됐다.

## 2. 설계 결정

### 2.1 데미지는 "펠릿 1개" 기준으로 적는다

산탄총의 `damage`는 한 발이 아니라 **펠릿 하나**의 피해다. 표기 위력(다 맞았을 때)을
적어두면 데이터만 보고는 한 펠릿이 얼마인지 알 수 없고, 판정 코드가 나눗셈을 해야 한다.
"다 맞으면 강하다"는 밸런스 의도는 `pellets × damage`로 읽으면 된다.

### 2.2 공격력 보너스는 발사 한 곳에서만 곱한다

음식으로 올린 공격력은 `fireOneShot()` 하나에서 근접·투사체·산탄 모두에 곱한다.
무기 종류마다 따로 곱하면 나중에 새 무기가 들어올 때 조용히 빠뜨린다.

### 2.3 최대 체력을 상수에서 엔티티로 올렸다

`wavesData.playerHp`를 직접 읽던 자리가 회복 상한·부활·HP바까지 여섯 군데 있었다.
음식으로 최대치가 늘어나므로 `World.playerMaxHp(player)` 하나를 거치게 바꿨고,
클라이언트도 상수 대신 서버가 내려준 `maxHp`로 비율을 계산한다.

### 2.4 이동속도 배율을 동기화한다

`stepPosition`에 `speedMultiplier`를 받도록 넓히고, 서버가 `PlayerSchema.speedMultiplier`로
내려준다. 클라이언트 예측이 같은 배율을 쓰지 않으면 아드레날린이 켜져 있는 10초 내내
캐릭터가 되감긴다(rubber-banding).

### 2.5 진통제는 "겹치면 긴 쪽"

같은 버프를 다시 쓰면 남은 시간에 **더하지 않고** 둘 중 긴 쪽으로 갱신한다. 더하기로 두면
쟁여놓고 연타해서 사실상 무적이 된다.

## 3. 도중에 드러난 버그: 빠른 총알이 적을 통과한다

저격 라이플(900px/s)을 넣고 관통 테스트를 짰더니 **아무것도 맞지 않았다.**

원인은 관통이 아니라 충돌 판정 자체였다. 투사체 충돌은 매 틱 **현재 위치 한 점**이
몬스터 원과 겹치는지만 봤는데, 900px/s면 한 틱(1/60초)에 15px을 건너뛴다. 잡몹 지름이
20px 남짓이라 조준이 정확해도 몸을 그냥 지나칠 수 있었다.

기존 무기들(최고 600px/s = 10px/틱)에서는 잘 드러나지 않았을 뿐, **새 무기가 만든 버그가
아니라 원래 있던 구멍**이다.

→ `projectileSweepHits()`를 만들어 판정을 점이 아니라 **선분(직전 위치 → 현재 위치)**으로
바꿨다. 투사체에 `prevX/prevY`를 남기고, 선분과 원 중심의 최단거리로 판정한다. 몬스터뿐
아니라 장애물(벽·자원 노드·콜로니)에도 같은 판정을 쓴다 — 빠른 총알이 벽을 뚫으면 안 된다.
격자 후보 질의 반경에도 이번 틱 이동거리를 더해야 그 구간의 몬스터가 후보에서 빠지지 않는다.

## 4. 에셋 — 픽셀을 재서 데이터로 옮겼다

새 무기 시트는 235×62 캔버스에 18종이 **전부 수평·우향**으로 그려져 있다(구 시트는
128×64에 기울어진 구도가 섞여 있었다).

측정 순서는 이렇다.

1. Aseprite CLI로 프레임을 뽑아 **불투명 픽셀 경계**를 잰다
2. 그립(손)·총구(축의 끝)를 정하고, 확대 이미지로 눈으로 검증한다
3. 화면에 보일 목표 길이를 정해 `scale = 목표 / 실제 길이`를 구한다
4. `muzzleOffset = 궤도반경(9) + 총구거리 × scale`을 **weapons.json에 역산해 넣는다**

4번이 핵심이다. 클라이언트는 `orbitRadius = muzzleOffset - 그림상 총구거리`로 궤도를
거꾸로 구하므로, 데이터와 그림이 항상 같은 지점을 가리킨다. 스프라이트를 다시 그려도
한쪽만 고쳐서 어긋날 일이 없다.

표창은 팩에 없어서 `assets/_generators/weapon_shuriken.lua`로 생성했다 — 4날 별은
완전히 규칙적인 도형이라 스크립트가 잘 맞는다.

## 5. 인벤토리 아이콘이 실 한 가닥이 됐다

무기 캔버스가 235×62(가로세로비 3.8)라, 정사각형 칸에 가로를 맞추면 세로가 8px밖에
안 남는다. 실제로 퀵슬롯에서 무엇을 들고 있는지 분간이 안 됐다.

두 가지를 같이 했다.

- **캔버스가 아니라 그림이 차지하는 영역으로 맞춘다**(`artBounds`). 18종이 같은 캔버스를
  공유해서, 권총처럼 작은 그림은 여백까지 칸을 차지해 3분의 1로 쪼그라들었다.
- **가로세로비가 2.2를 넘으면 -30°로 눕힌다.** 칸의 대각선을 쓰게 되어 1.4배쯤 커진다.

## 6. 검증

- shared 461개 / server 31개 테스트 통과. 신규 규칙은 `world-weapons.test.ts` 20개
- 헤드리스 크롬으로 실제 렌더 확인: 19종 착용 자세, 산탄 6발 부채꼴, 탄약/재장전 HUD,
  점사 표시, 빔소드 야간 조명

## 7. 남은 것

- 상점 진열은 `items.json`의 `rarity`+`buyPrice`로 자동 후보가 된다 — 신규 무기 19종이
  전부 들어가므로 등급별 가중치(`shop.json`) 재조정이 필요할 수 있다
- 스태미나는 아직 게이지가 없어 음식의 "스태미나 +"를 이동속도로 해석했다. 게이지가
  생기면 `statBonus.stat === 'stamina'` 처리를 그쪽으로 옮긴다
- 제작(`crafting.json`)은 여전히 도구 8종뿐이다. 신규 무기의 제작 경로는 미정

## 8. 후속 조정 (같은 날)

플레이 확인 후 다섯 가지를 손봤다.

### 8.1 무기 렌더 크기 2배

캐릭터(32px) 옆에서 총이 너무 작아 무엇을 들었는지 안 보였다. 렌더 배율을 전부 2배로
올렸고, **그에 맞춰 데이터도 같이 움직였다.**

- 원거리: `muzzleOffset`을 새 배율로 다시 역산했다(예: 저격 32 → 55). 안 하면 총알이
  총구가 아니라 총열 중간에서 튀어나온다.
- 근접: `range`를 그린 길이에 맞췄다(뭉둥이 30 → 55, 빔소드 38 → 69). **밸런스가 함께
  바뀐다** — 근접 사거리가 거의 2배가 되어 잡몹 사거리(20~24)를 크게 앞선다. 그림과 판정이
  어긋나는 것보다는 낫다고 봤지만, 세다고 느껴지면 `weapons.json`의 `range`만 낮추면 된다
  (그 경우 "칼이 닿는데 안 맞는" 구간이 생긴다).

### 8.2 재장전 게이지

캐릭터 이름표 바로 위에 얇은 막대를 얹어 왼쪽부터 채운다. 처음엔 이름표 아래(머리 위)에
뒀는데 머리카락에 겹쳐서 위로 올렸다. 진행률은 `reloadRemaining ÷ 무기의 reloadTime`으로
클라이언트가 계산한다 — 총 시간은 이미 데이터에 있어 동기화 필드를 늘릴 이유가 없다.

### 8.3 잡몹 공격 주기 완화

너무 빨라서 붙으면 손쓸 틈이 없었다. 40% 가량 늘렸다(헬하운드 0.8 → 1.2, 데몬 1.0 → 1.5,
블러드 1.0 → 1.4, 아이볼 1.2 → 1.7, 라바슬라임 1.5 → 2.0, 미노타우르스 1.2 → 1.7).
보스는 이미 따로 조율한 값이라 건드리지 않았다.

### 8.4 코어 피격 연출

코어를 감싸며 커지던 얇은 붉은 **원**을 걷어내고, 캐릭터 피격과 같은 문법 —
**실루엣을 밀어 깔아 만든 외곽선** — 으로 바꿨다. 코어 그림이 원형이 아니라 원 테두리가
어디에도 닿지 않고 공중에 떠 보였다. 색은 캐릭터보다 어둡게 눌러(0xa8322a) 코어의 청록색과
부딪히지 않게 했고, 두 번 깜빡인다. 두께는 그림이 커서 2px이다(캐릭터는 1px).

### 8.5 코어를 때릴 때 공격 모션이 안 나오던 문제

**원인은 코어가 아니라 신호 방식이었다.** 클라이언트는 "공격 중"(`attacking`) 불리언의
false→true 전이로 모션을 재생했는데, 모션 길이(예고 0.36 + 0.4초 = 0.76초)가 공격
주기와 거의 같은 몬스터는 **꺼져 있는 구간이 40ms**뿐이다(헬하운드 0.8초 주기). 상태
동기화는 20Hz(50ms)라 그 창을 통째로 건너뛰기 일쑤였고, 그러면 클라이언트 눈에는 플래그가
계속 켜져 있어서 **첫 공격 이후 모션이 영영 재생되지 않았다.** 코어처럼 쉬지 않고 때리는
상황에서 두드러졌을 뿐, 대상과는 무관한 버그다.

→ 공격을 시작할 때마다 1씩 오르는 `attackSeq`(uint8, 한 바퀴 돌려 씀)를 몬스터에 붙이고,
클라이언트는 **이 값이 달라지는 순간** 재생한다. 값이 바뀐 사실만 보면 되므로 관측 타이밍과
무관하다. 8.3의 주기 완화도 이 창을 넓혀 주지만, 그건 완화지 해결이 아니다.

회귀 테스트는 실제 클라이언트와 같은 20Hz로만 관측하면서 번호가 여러 번 바뀌는지 본다
(`world-combat.test.ts`).

## 9. 재조정 2차

### 9.1 무기 크기를 컨셉별로 다시 잡았다

일괄 2배는 작은 총까지 과하게 커졌다. **기본을 원본의 1.5배**로 낮추고, 무기 컨셉에 따라
2.0배까지 올렸다.

| 배율 | 무기 |
|---|---|
| 1.5 | 권총·리볼버·기관단총·새총·표창·나이프·토마호크 |
| 1.6~1.7 | 마체테·소방도끼·뭉둥이·돌격소총·빔소드 |
| 1.8~1.85 | 석궁·펌프샷건·더블배럴·장전식 소총·돌창 |
| 2.0 | 저격 라이플·미니건 |

`muzzleOffset`(원거리)과 `range`(근접)도 매번 함께 다시 계산한다 — 그림과 판정이 같은
곳을 가리켜야 한다는 원칙은 그대로다. 근접 사거리는 2차 조정으로 조금 내려왔다
(뭉둥이 55 → 47, 빔소드 69 → 60).

### 9.2 보스는 "평타 + 스킬"이 아니라 패턴 3개다

보스도 잡몹과 같은 평타 경로(`startBasicAttack`)를 타고 있었고, 그 평타가 Attack01을
재생했다. 그래서 **같은 그림이 평타와 1번 기술 양쪽으로 쓰이며 서로를 덮어썼다.**

- `startBasicAttack`은 `meleeAttacks`를 가진 타입에서 즉시 반환한다 — 보스에겐 평타가 없다.
- 패턴 선택에 **가중치**(`weight`)를 넣었다. 쿨다운이 "언제 다시 쓸 수 있나"라면 가중치는
  "쓸 수 있을 때 얼마나 자주 고르나"다. 둘 다 있어야 큰 기술이 쿨다운이 도는 즉시 반드시
  나오는 기계적인 순서가 되지 않는다. 1번은 짧은 쿨다운 + 높은 가중치(5)라 자연스럽게
  자주 나오는 동작이 되고, 3번은 길고 드물다(가중치 1).
- 평타가 없어졌으므로 **패턴이 코어와 벽도 때린다**(`resolveMeleeHit`). 안 그러면 보스가
  코어를 부술 방법 자체가 사라진다.
- 대상 선택도 한곳으로 모았다(`bossPatternTarget`): 사람 → (검이 닿는 거리의) 티모시 → 코어.
  처음엔 티모시를 아그로 반경(수백 px)으로 잡았다가, 멀리 있는 티모시를 겨눈 채 사거리
  밖이라 아무것도 못 하고 코어 앞이라 움직이지도 않는 **교착**에 빠졌다. 쫓아갈 대상은
  사람뿐이다.

### 9.3 골렘 돌격을 직사각형 통로로

원 판정은 **폭이 곧 사거리**라 길게 만들수록 사방이 넓어져서 옆으로 피할 방향이 사라진다.
그래서 돌진에 `halfWidth`를 넣고, 있으면 **출발점에서 현재 위치까지의 직사각형**으로
판정한다 — 길이(돌진 거리)와 폭을 따로 정할 수 있다.

골렘 3번은 스프라이트가 실제로 앞으로 튀어나가는 구간(프레임 4~8 = 0.44~0.89초)에 맞춰
0.45초 동안 420px/s로 **189px**을 밀고 나간다(예전 45px). 폭은 좌우 46px. 마무리 광역은
돌진 도중(0.67초)이 아니라 **끝나는 자리**(0.89초)에서 터진다 — 앞으로 나가기도 전에
판정이 끝나 있었다.

예고도 같이 고쳤다. 마무리 광역만 예고하면 화면엔 보스 발밑의 원만 뜨는데 정작 위험한 건
앞으로 밀고 나가는 통로다 — **예고와 판정이 다르면 피할 방법이 없다.** 돌진이 있는 기술은
지나갈 길을 띠로 먼저 보여준다.
