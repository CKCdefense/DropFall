# 52. 무기·아이템 전면 재설계 (작업 보고)

기존 13종(권총/매그넘/소총/산탄총/미니건/빔소드 + 도구 7종)을 걷어내고, 티어가 있는
**근접 7종 + 원거리 12종**과 **치료 5종 + 음식 6종**으로 갈아엎었다. 에셋도 새 팩
(`weapons_new.aseprite`, `item_usable.aseprite`)으로 교체했다.

## 1. 무엇이 새로 생겼나

기존 시스템에는 없던 규칙들이 이번에 들어왔다.

| 기능 | 어디에 |
|---|---|
| 탄창·재장전 | `WeaponAmmo` (sim/combat.ts) |
| 산탄(펠릿 여러 발) | `resolveFire`가 배열을 반환 |
| 관통 | `ProjectileEntity.pierce` + `hitIds` |
| 점사 모드 | `World.bursts` + `toggleFireMode` |
| 소모품 버프(진통제·아드레날린) | `PlayerEntity.hpFloorTimer` / `speedBuffTimer` |
| 음식 영구 스탯 | `maxHpBonus` / `attackBonus` / `staminaBonus` |
| 채집 효율 분리 | `weapons.json`의 `gatherMultiplier` |
| 무기별 사거리 | `weapons.json`의 `maxRange` |
| 야간 조명 | `weapons.json`의 `lightRadius` (클라 연출 전용) |

`magazine`/`reloadTime`은 예전부터 데이터에만 있고 아무도 읽지 않는 **죽은 필드**였다.
이번에 실제로 쓰이게 됐다.

## 2. 설계 결정

### 2.1 데미지는 "펠릿 1개" 기준으로 적는다

산탄총의 `damage`는 한 발이 아니라 **펠릿 하나**의 피해다. 표기 위력(다 맞았을 때)을
적어두면 데이터만 보고는 한 펠릿이 얼마인지 알 수 없고, 판정 코드가 나눗셈을 해야 한다.
"다 맞으면 강하다"는 밸런스 의도는 `pellets × damage`로 읽으면 된다.

### 2.2 공격력 보너스는 발사 한 곳에서만 곱한다

음식으로 올린 공격력은 `fireOneShot()` 하나에서 근접·투사체·산탄 모두에 곱한다.
무기 종류마다 따로 곱하면 나중에 새 무기가 들어올 때 조용히 빠뜨린다.

### 2.3 최대 체력을 상수에서 엔티티로 올렸다

`wavesData.playerHp`를 직접 읽던 자리가 회복 상한·부활·HP바까지 여섯 군데 있었다.
음식으로 최대치가 늘어나므로 `World.playerMaxHp(player)` 하나를 거치게 바꿨고,
클라이언트도 상수 대신 서버가 내려준 `maxHp`로 비율을 계산한다.

### 2.4 이동속도 배율을 동기화한다

`stepPosition`에 `speedMultiplier`를 받도록 넓히고, 서버가 `PlayerSchema.speedMultiplier`로
내려준다. 클라이언트 예측이 같은 배율을 쓰지 않으면 아드레날린이 켜져 있는 10초 내내
캐릭터가 되감긴다(rubber-banding).

### 2.5 진통제는 "겹치면 긴 쪽"

같은 버프를 다시 쓰면 남은 시간에 **더하지 않고** 둘 중 긴 쪽으로 갱신한다. 더하기로 두면
쟁여놓고 연타해서 사실상 무적이 된다.

## 3. 도중에 드러난 버그: 빠른 총알이 적을 통과한다

저격 라이플(900px/s)을 넣고 관통 테스트를 짰더니 **아무것도 맞지 않았다.**

원인은 관통이 아니라 충돌 판정 자체였다. 투사체 충돌은 매 틱 **현재 위치 한 점**이
몬스터 원과 겹치는지만 봤는데, 900px/s면 한 틱(1/60초)에 15px을 건너뛴다. 잡몹 지름이
20px 남짓이라 조준이 정확해도 몸을 그냥 지나칠 수 있었다.

기존 무기들(최고 600px/s = 10px/틱)에서는 잘 드러나지 않았을 뿐, **새 무기가 만든 버그가
아니라 원래 있던 구멍**이다.

→ `projectileSweepHits()`를 만들어 판정을 점이 아니라 **선분(직전 위치 → 현재 위치)**으로
바꿨다. 투사체에 `prevX/prevY`를 남기고, 선분과 원 중심의 최단거리로 판정한다. 몬스터뿐
아니라 장애물(벽·자원 노드·콜로니)에도 같은 판정을 쓴다 — 빠른 총알이 벽을 뚫으면 안 된다.
격자 후보 질의 반경에도 이번 틱 이동거리를 더해야 그 구간의 몬스터가 후보에서 빠지지 않는다.

## 4. 에셋 — 픽셀을 재서 데이터로 옮겼다

새 무기 시트는 235×62 캔버스에 18종이 **전부 수평·우향**으로 그려져 있다(구 시트는
128×64에 기울어진 구도가 섞여 있었다).

측정 순서는 이렇다.

1. Aseprite CLI로 프레임을 뽑아 **불투명 픽셀 경계**를 잰다
2. 그립(손)·총구(축의 끝)를 정하고, 확대 이미지로 눈으로 검증한다
3. 화면에 보일 목표 길이를 정해 `scale = 목표 / 실제 길이`를 구한다
4. `muzzleOffset = 궤도반경(9) + 총구거리 × scale`을 **weapons.json에 역산해 넣는다**

4번이 핵심이다. 클라이언트는 `orbitRadius = muzzleOffset - 그림상 총구거리`로 궤도를
거꾸로 구하므로, 데이터와 그림이 항상 같은 지점을 가리킨다. 스프라이트를 다시 그려도
한쪽만 고쳐서 어긋날 일이 없다.

표창은 팩에 없어서 `assets/_generators/weapon_shuriken.lua`로 생성했다 — 4날 별은
완전히 규칙적인 도형이라 스크립트가 잘 맞는다.

## 5. 인벤토리 아이콘이 실 한 가닥이 됐다

무기 캔버스가 235×62(가로세로비 3.8)라, 정사각형 칸에 가로를 맞추면 세로가 8px밖에
안 남는다. 실제로 퀵슬롯에서 무엇을 들고 있는지 분간이 안 됐다.

두 가지를 같이 했다.

- **캔버스가 아니라 그림이 차지하는 영역으로 맞춘다**(`artBounds`). 18종이 같은 캔버스를
  공유해서, 권총처럼 작은 그림은 여백까지 칸을 차지해 3분의 1로 쪼그라들었다.
- **가로세로비가 2.2를 넘으면 -30°로 눕힌다.** 칸의 대각선을 쓰게 되어 1.4배쯤 커진다.

## 6. 검증

- shared 461개 / server 31개 테스트 통과. 신규 규칙은 `world-weapons.test.ts` 20개
- 헤드리스 크롬으로 실제 렌더 확인: 19종 착용 자세, 산탄 6발 부채꼴, 탄약/재장전 HUD,
  점사 표시, 빔소드 야간 조명

## 7. 남은 것

- 상점 진열은 `items.json`의 `rarity`+`buyPrice`로 자동 후보가 된다 — 신규 무기 19종이
  전부 들어가므로 등급별 가중치(`shop.json`) 재조정이 필요할 수 있다
- 스태미나는 아직 게이지가 없어 음식의 "스태미나 +"를 이동속도로 해석했다. 게이지가
  생기면 `statBonus.stat === 'stamina'` 처리를 그쪽으로 옮긴다
- 제작(`crafting.json`)은 여전히 도구 8종뿐이다. 신규 무기의 제작 경로는 미정
