# 작업 보고서 — 코어 업그레이드(에너지 소비) + 정적 오브젝트 하드 충돌

> 두 가지를 이어서 구현했다: (1) backend/37에서 만든 "에너지"의 첫 소비처인
> 코어 업그레이드(체력+건설 반경+제작/스텟증가 해금, 3단계) — `UpgradeModal`
> (frontend/09)의 플레이스홀더 버튼에 처음으로 실제 서버 액션을 연결했다.
> (2) 코어/자원 노드/콜로니를 몬스터·플레이어·투사체가 통과 못 하게 막는
> 하드 충돌. 후자를 구현하다가 "FlowField가 셀 단위로 우회를 계산해 주니
> 몬스터 쪽엔 따로 손댈 게 없다"는 최초 판단이 실제로는 틀렸다는 걸 테스트로
> 직접 재현해서 발견하고 고쳤다 — 아래 §2.2에 그 과정을 남긴다.

---

## 1. 기획 — 무엇을, 왜

"코어업그레이드 - 에너지 자원을 사용해서 코어 체력 + 건설가능한 영토 증가 +
제작, 플레이어 캐릭터 스텟 증가 해금 (3단계 구상중)"과 "각 오브젝트(코어,
나무, 돌, 콜로니)등등을 통과하지 못하게 (몹, 플레이어, 총알)하고자함"이라는
요청. 구현 전에 두 가지를 확인했다:

- **몬스터가 막혔을 때 건축물처럼 공격해서 부술 수 있게 할까, 그냥 통과만
  못 하게 막을까** → **통과만 막는다(파괴 불가)**로 확정. 자원 노드는 이미
  채집(리스폰) 메커니즘이 있어 "파괴"라는 개념이 안 맞고, 콜로니는 몬스터
  자신의 스폰원이라 몬스터가 그걸 공격하는 것도 이상하다.
- **`UpgradeModal`이 이미 버튼 3개(티어 증가/토지 확장/코어 수리)를 갖고
  있었다.** 요청 내용("체력+영토+해금이 한 번에 일어나는 3단계")은 **"티어
  증가" 버튼 하나**에 그대로 대응된다고 판단해 거기에만 연결했다 — "토지
  확장"/"코어 수리"는 이번 요청에 없는 별개 개념이라 손대지 않았다.

## 2. 과정 — 어떻게 했나

### 2.1 코어 업그레이드

`coreUpgrades.json`(신규)에 3단계를 정의했다 — 각 단계는 비용(에너지)과 코어
체력 보너스, 건설 반경 보너스, 제작/스텟증가 해금 여부를 함께 갖는다:

```json
{
  "baseBuildRadius": 250,
  "tiers": [
    { "cost": 5,  "coreHpBonus": 200, "buildRadiusBonus": 150, "unlocksCrafting": false, "unlocksStatUpgrades": false },
    { "cost": 10, "coreHpBonus": 300, "buildRadiusBonus": 200, "unlocksCrafting": true,  "unlocksStatUpgrades": false },
    { "cost": 20, "coreHpBonus": 500, "buildRadiusBonus": 300, "unlocksCrafting": true,  "unlocksStatUpgrades": true }
  ]
}
```

`World.upgradeCore(playerId)`가 `core.tier`번째(0-based) 단계를 팀 공유
에너지로 사고, 코어 체력(즉시 회복 + 최대치)·건설 반경·해금 플래그를 한 번에
적용한다. `getBuildRadius()`는 구매한 단계만큼 `baseBuildRadius`에 누적하고,
`placeBuilding()`은 설치하려는 셀이 이 반경 밖이면 거절한다.

"제작 해금"은 실제로 뭔가 있는 게 아니라 아직 빈 `CraftModal`을 열 수 있는지
여부를 게이팅하는 정도이고, "스텟 증가 해금"은 그걸 쓸 UI/구매 로직 자체가
없어서 `isStatUpgradesUnlocked()` 플래그만 만들어 뒀다 — 둘 다 §4에 다음
작업으로 명시한다.

### 2.2 정적 오브젝트 하드 충돌 — 처음 판단이 틀렸던 부분

**플레이어**: `isBlockedForPlayer()`(기존 건축물 하드 충돌 함수)에 자원 노드
(`resourcesData[type].hitRadius`)·콜로니(`COLONY_RADIUS=14`, colony.ts에 신규
export)·코어(`CORE_RADIUS`, 원점 고정) 검사를 추가했다. `movePlayer()`의
3단계 축 슬라이딩은 그대로 재사용 — 판정 함수만 넓혔다.

**투사체**: `projectileHitsBuilding()`을 `projectileHitsObstacle()`로 확장해
같은 세 가지를 추가했다. 건축물은 `blocksProjectile` 타입(벽)만 막지만,
자원/콜로니/코어는 예외 없이 전부 막는다(사용자가 넷 다 막아달라고 명시).
맞으면 투사체만 사라지고 대상은 피해를 입지 않는다(파괴 불가 원칙과 일치).

**몬스터 — 처음 설계**: 자원 노드/콜로니는 게임 내내 위치가 고정이라
(설치/파괴 이벤트가 없다), 생성 시점에 셀을 한 번만 계산해 캐싱하는
`staticObstacleCells` 집합을 만들고 FlowField의 `isBlocked` 콜백이 이걸 같이
보게 했다. 이때 **코어 자신의 셀은 절대 이 집합에 넣지 않는다** — FlowField의
목표(target) 셀이 막히면 `recompute()`가 전체 계산을 포기해버리는 치명적인
경우라서다(몬스터는 어차피 `attackRange + CORE_RADIUS`에서 멈춰 코어를
공격하므로 코어 셀을 막을 이유도 없다). 여기까지 하고 "코어로 걸어가는
분기는 FlowField가 이미 자원/콜로니를 우회 경로로 계산해 주니 따로 손댈 게
없다"고 판단해서, 몬스터 쪽엔 목표를 향해 직선으로만 움직이는 "타겟 추격"
분기에만 막힘 검사(`findBlockingStaticObstacle`, 건축물의
`findBlockingBuildingInRange`를 본떴지만 공격 대신 그냥 멈추게 함)를 추가하고
넘어갔다.

**테스트로 재현해서 발견한 문제**: 검증 테스트를 짜면서("코어로 걸어가는
몬스터가 콜로니를 우회하는지") 몬스터를 콜로니-코어 연장선 위, 콜로니보다
먼 지점에 두고 500틱 동안 접근시키며 콜로니까지의 최소 거리를 추적했더니 —
최소 거리가 사실상 0(콜로니 중심을 그대로 통과)이 나왔다. 원인:
**FlowField는 셀(16px) 단위로만 막힘을 판정하는데, 콜로니/자원 노드의 실제
충돌 원(14px)은 셀 경계와 정확히 안 맞는다.** "셀 기준으로는 우회 경로"인데
그 경로가 실제 충돌 원의 코너를 스치듯 지나가면서 중심 근처까지 파고드는
상황이 실제로 나왔다. FlowField가 "막혔다/안 막혔다"를 계산하는 해상도와
실제 하드 충돌 판정(원)의 해상도가 다르다는 걸 놓친 것이었다.

**수정**: "코어로 걸어가기" 분기에도 `moveMonster()` 호출 직전에 같은
`findBlockingStaticObstacle` 검사를 추가했다 — FlowField가 계산한 방향으로
움직이려는 순간, 사거리 안에 자원/콜로니가 있으면 셀 판정과 무관하게 그냥
멈춘다. 셀 기반 라우팅(FlowField)이 큰 그림의 우회를, 사거리 기반 하드
스톱(`findBlockingStaticObstacle`)이 마지막 몇십 px의 정밀도를 담당하는
2단 방어로 정리했다.

## 3. 결과 — 검증

```bash
pnpm --filter @dropfall/shared test   # 17 files, 247 tests 전부 통과(신규 13개)
pnpm --filter @dropfall/server typecheck   # 순차 실행(동시 -r 실행 시 이 환경 OOM)
pnpm --filter @dropfall/client typecheck
pnpm lint      # 에러 0
pnpm build     # client(vite)/server(tsup) 전체 통과
```

새 테스트: `coreUpgrade.test.ts`(6개) — 구매 시 비용 차감/체력·반경 증가,
에너지 부족 거절, 최고 단계 이후 거절, 존재하지 않는 플레이어 무시, 해금
플래그가 그 단계부터 계속 유지됨, 건설 반경 밖 거절→업그레이드 후 허용.
`world-building.test.ts`에 추가한 하드 충돌 테스트(13개) — 자원 노드/콜로니/
코어 각각의 플레이어 충돌·투사체 차단, 추격 중인 몬스터가 자원/콜로니에
막히면 공격 없이 멈춤, 콜로니가 직선 경로를 막으면 몬스터가 실제로 충돌
반경 밖으로 우회함(500틱 추적), 코어 자신은 FlowField를 깨지 않고 몬스터가
여전히 도달해 공격하는 회귀 테스트.

**부수 작업**: 새 건설 반경 제한 때문에 기존 건축 관련 테스트 다수가 실패했다
— `world-building.test.ts`의 테스트는 대부분 코어에서 멀리 떨어진 좌표
(예: (550,500))에 건축물을 짓는데, 이게 이번에 새로 생긴 반경 제한(기본
250px)에 걸렸다. `createTestWorld()`가 항상 최고 티어로 시작하도록 고쳐서
(자원 비용 제약을 없애는 기존 `grantSharedResources` 헬퍼와 같은 방식) 대부분
해결했고, 최고 티어 반경(900px)도 넘는 극단적 좌표(800,800) 3곳만 더 가까운
좌표(500,500)로 옮겼다.

## 4. 다음 작업

- **"토지 확장"/"코어 수리" 버튼 미배선** — `UpgradeModal`에 이미 있는 버튼인데
  이번 요청 범위 밖이라 손대지 않았다. 반복 구매형 확장인지, 코어 HP를
  에너지 없이 응급 회복하는 기능인지 등 별도 설계가 필요하다.
- **플레이어 스텟 증가 시스템 자체가 없음** — `isStatUpgradesUnlocked()` 플래그만
  존재하고, 실제로 뭘 올릴 수 있는지(공격력? 이동속도? 체력?), UI는 어떻게
  생겼는지 전혀 미정이다.
- **제작 콘텐츠 없음** — `CraftModal`이 해금은 되지만 여전히 빈 껍데기다.
- **건설 가능 영토의 시각적 구분 없음** — 사용자가 "특정 타일을 배치해서
  나중에 구분지을 예정"이라고 명시했다 — 지금은 반경을 벗어나면 그냥 조용히
  거절될 뿐, 화면에 "여기까지 지을 수 있다"는 표시가 없다.
- **밸런스 값 전부 임의값** — 코어 업그레이드 비용/보너스, `baseBuildRadius`
  모두 플레이테스트 후 조정 대상이다.
