# 작업 보고서 — 몬스터가 자원 군집에 완전히 막히면 못 벗어나는 버그 + 클라이언트 외삽이 장애물을 뚫고 지나가 보이는 버그

> 스크린샷과 함께 "지나갈 수 없다고 판단되면 돌아오는 로직이 있어야 할 것
> 같다"와 "몬스터가 자원엔티티를 뚫고 지나가는 모습이 보였다"는 두 제보를
> 받았다. 조사해보니 완전히 다른 두 버그였다 — 하나는 서버 시뮬레이션(몬스터가
> 촘촘한 군집에 진짜로 갇힘), 하나는 클라이언트 렌더링(서버는 절대 안 뚫는데
> 화면에서만 뚫려 보임)이었다. 둘 다 무작위 스트레스 테스트로 재현·확진한 뒤
> 고쳤다.

---

## 1. 기획 — 무엇을, 왜

원문 제보: "지나갈수 없다고 판단되면 돌아오는 로직이 있어야할거같고", "지금
몬스터가 자원엔티티를 뚫고 지나가는 모습이 보였어". 후자에 대해 "고갈된(반투명)
노드였는지, 멀쩡한(진한) 노드였는지" 물었고 **"진하게 보였다(멀쩡한 노드)"**는
답을 받아 — 고갈 노드가 통과 가능한 건 의도된 동작(docs/backend/39)이라 그
가능성은 배제하고, 진짜 관통 버그로 보고 조사를 시작했다.

## 2. 과정 — 어떻게 했나

### 2.1 재현 — 서버는 절대 안 뚫는다는 것부터 확인

먼저 `_debug.test.ts` 스크래치 테스트로 두 제보를 각각 재현·확진했다:

- **고착(버그 1)**: `MIN_NODE_SPACING`(36px)에 가까운 노드 6개를 육각형 고리로
  배치하고 코어-군집 연장선 바깥에서 코어로 걸어오게 하니, 군집 경계에서 60초
  내내 완전히 멈췄다. 60개 무작위 설정(군집 크기/간격/접근각/몬스터 타입)으로
  반복하니 3/60(약 5%)에서 "코어에도 못 가고 군집에 완전히 갇힘"이 재현됐다 —
  docs/backend/40에서 이미 "여러 노드가 촘촘히 둘러싸면 이론상 못 움직일 수
  있다"고 범위 밖으로 남겨둔 한계가 실제로 일어난 것이었다.
- **관통(버그 2)**: 같은 스트레스 테스트를 실제 서버 틱레이트(1/60초)로 단일/
  다중 몬스터 90회 이상 돌렸는데, **서버 시뮬레이션은 단 한 번도 실제 충돌
  반경을 침범하지 않았다.** `isBlockedForMonster`가 매 틱 목적지를 정확히
  검사하므로 당연한 결과다. 그렇다면 사용자가 본 건 뭐였을까 — 클라이언트
  `SnapshotInterpolator.ts`의 `extrapolateList()`(스냅샷이 늦게 도착할 때
  마지막 속도로 최대 100ms 앞질러 그리는 dead-reckoning, docs/backend/14)를
  다시 보니 **장애물을 전혀 모르고 순수 속도 외삽만 하고 있었다.** 보스 돌진
  (260px/s)은 100ms 동안 최대 26px까지 미리 그릴 수 있는데, 자원 노드 지름
  (28px)과 맞먹는다 — 서버가 노드 앞에서 막았어도 클라이언트 화면에서는 마지막
  속도 방향으로 노드를 뚫고 그려질 수 있었다. "진하게 보이는 노드를 뚫었다"는
  제보와 정확히 일치했다.

### 2.2 몬스터 탈출 점프

`MonsterEntity`에 `stuckSeconds` 필드를 추가하고, `moveMonster`가 완전히
자유로운(폴백 없는) 이동에 성공할 때만 0으로 리셋하도록 했다. 처음엔 "폴백
(축 슬라이딩/접선 미끄러짐) 성공도 리셋"으로 짰는데, 이러면 **실제로는 전혀
전진 못 하면서 매 틱 아주 미세하게(0.0001px 단위로) 위치가 바뀌는 것만으로
"이동 성공"으로 잘못 인정돼 탈출 로직이 영원히 발동하지 않는 버그**가 새로
생겼다 — 스트레스 테스트로 잡았다. 자원 노드와 정확히 같은 x/y축으로
접근하면(흔한 배치) x-only/y-only 축 슬라이딩 검사가 "제자리(dx 또는 dy가
0)"를 "성공"으로 착각하는 게 근본 원인이었다. 두 가지로 고쳤다: (1) dx/dy가
실제로 0이 아닐 때만 그 축의 결과를 인정, (2) 폴백을 썼다는 것 자체를 "아직
막혀 있다"는 신호로 보고 `stuckSeconds`는 계속 쌓이게 하되(단, 완전 자유
이동일 때만 리셋), 임계값(`STUCK_ESCAPE_SECONDS=1.5초`, 정상적인 모서리
우회는 보통 1초 안에 끝나므로 여유를 뒀다)을 넘기면 가장 가까운 장애물 반대
방향으로 40px 점프(`STUCK_ESCAPE_DISTANCE`, 기존 배치 재시도 패턴과 같은 최대
8회 각도 재시도)를 시도한다.

### 2.3 클라이언트 외삽 장애물 인지

`packages/shared/src/index.ts`에 `circlesOverlap`(combat.ts)과
`COLONY_RADIUS`(colony.ts)를 최소한으로 새로 공개했다(`HIT_RADIUS`/
`resourcesData`/`monstersData`는 이미 공개돼 있었다). `SnapshotInterpolator.ts`에
`wouldOverlapObstacle(x, y, entityRadius, resourceNodes, colonies)`를 추가해
서버의 `isBlockedForPlayer`/`isBlockedForMonster`와 같은 규칙(콜로니는 파괴돼도
폐허가 계속 막으므로 `destroyed` 무시)으로 검사하고, `extrapolateList`에
옵션 콜백을 추가해 **외삽 결과가 장애물과 겹치면 외삽을 포기하고 마지막으로
알려진(서버가 항상 안전을 보증하는) 위치를 그대로 쓰게** 했다. 플레이어·몬스터
에만 적용하고 투사체는 그대로 뒀다 — 빠르게 지나가 눈에 띄는 관통이 거의
없고, 막으면 오히려 총알이 허공에서 멈칫하는 게 더 어색하다.

### 2.4 탈출 방향 보정 — 장애물 반대쪽이 아니라 목표 쪽으로

처음 버전은 탈출 점프 방향을 "가장 가까운 장애물 반대쪽"으로 잡았다. 실제로
써보니(스크린샷 제보 — "점프는 X로 가지만 O로 가길 원한다") 갇힌 지점에서
원래 가려던 목표(코어/플레이어)와 **정반대 방향**으로 튕겨 나가는 경우가
많았다 — 장애물 하나만 피하면 된다고 판단했지 "결국 어디로 가고 싶은지"는
전혀 고려하지 않았기 때문이다. `tryEscapeStuckMonster`를 고쳐서, 원래 가려던
방향(정규화된 `normX/normY`)을 정면으로 두고 좌우로 부채꼴(22.5도씩 번갈아
확대, 최대 8회)을 벌려가며 처음 안 막힌 후보를 쓰도록 했다 — 목표를 완전히
등지는 방향보다 목표 쪽에 최대한 붙은 우회를 먼저 시도해야, 탈출 직후에도
계속 목표를 향해 나아갈 가능성이 높다.

## 3. 결과 — 검증

```bash
pnpm --filter @dropfall/shared test        # 17 files, 261 tests 전부 통과(신규 1개)
pnpm --filter @dropfall/server typecheck   # 순차 실행(동시 -r 실행 시 이 환경 OOM)
pnpm --filter @dropfall/client typecheck   # SnapshotInterpolator 타입 검증
pnpm lint      # 에러 0
pnpm build     # client(vite)/server(tsup) 전체 통과
```

신규 테스트(`world-building.test.ts`): 노드 6개짜리 촘촘한 고리에 몬스터를
가둔 뒤, (1) 실제로 갇히는 상황까지 재현되는지, (2) 결국 탈출하는지, (3) 탈출
점프를 포함해 전 과정에서 실제 충돌 반경을 한 번도 침범하지 않는지를 실제
서버 틱레이트로 확인한다. 기존 "그 자리에 완전히 멈춘다" 테스트 2개(docs/backend/40)는
탈출 점프 임계값(1.5초) 전 구간(0.9초)만 검증하도록 조정했다 — 그 이후엔 이제
정상적으로 탈출해야 하므로 예전 어서션(영원히 안 움직임)은 더 이상 맞지 않는다.

`SnapshotInterpolator.ts`는 `packages/client`에 테스트 러너가 없어(vitest
미설정) 자동 테스트를 추가하지 않았다 — typecheck + build + 코드 리뷰로
검증했다(이 파일의 기존 검증 방식과 동일).

## 4. 다음 작업

- **탈출 점프 값 임의값** — `STUCK_ESCAPE_SECONDS`(1.5초)/`STUCK_ESCAPE_DISTANCE`
  (40px) 모두 감으로 잡았다. 플레이테스트 후 조정 대상이다.
- **더 촘촘한(예: 3개 이상 겹겹이) 장애물 배치는 여전히 여러 번의 점프가
  필요할 수 있다** — 이번 수정으로 "영원히 멈춤"은 없어졌지만, 극단적인
  배치에서는 점프가 순간이동처럼 여러 번 보일 수 있다. 실사용에서 자주
  발생하면 자원 군집 생성 시 노드 간 최소 간격을 지금보다 넓히는 것도 고려할
  수 있다.
