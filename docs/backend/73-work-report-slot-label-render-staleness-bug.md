# 73. 작업 보고서 — 퀵무브/충전 칸 라벨이 화면에 고착되는 렌더링 버그 수정

## 기획

사용자 버그 제보(원문):

> 창고를 열었을 시점에 인벤토리에 아이템이 가득 차있으면 이후 인벤토리를
> 비우고 쉬프트 + 좌클릭으로 빠르게 아이템을 인벤토리로 가져오려 했을 때
> 인벤토리가 가득차있는것으로 인식해 해당 기능이 적용되지않는 버그

추가 확인 질문에 대한 답변으로 범위가 넓어졌다:

> (혼자하기/멀티 둘 다 재현되나요) 둘다 반대로 코어에 자원화할 자원들
> 삽입할때도 코어 업그레이드해서 칸이 늘어났어도 해당 모달을 닫고 다시 열지
> 않는이상 계속 막혀있는 판정이라 쉬프트클릭, 드래그앤드롭으로 해당 위치에
> 집어넣기 불가능
>
> (재시도 시 화면 반응) 아무 반응도 없음(클릭이 안 들어간 것처럼)

## 과정

### 1. 코드 리뷰로는 원인을 못 찾음

서버(`World.quickMoveItem`/`moveItem`/`Inventory`/`CoreStorage`), 서버→클라
Colyseus 스키마 동기화, 클라이언트(`SlotDrag`의 드래그·퀵무브 로직,
`HudScene`의 배선, `WarehousePanel`/`CoreModal`의 탭 상태 체크,
`SnapshotInterpolator`의 스냅샷 보간)를 전부 훑었지만 "모달을 연 시점에
캐싱된 상태가 고착되는" 경로를 찾지 못했다. `World.quickMoveItem`을 그대로
재현하는 유닛 테스트(가득 채움 → 거절 확인 → 완전히 비움 → 재시도)도
작성해서 돌려봤는데 **정상 통과** — 서버 로직 자체는 결백했다.

### 2. Playwright로 실제 브라우저 재현

정적 분석이 막혀서 실제로 게임을 띄우고 재현하기로 했다. Playwright +
Chromium을 이 세션에 새로 설치하고, `?local=1`(혼자하기, 서버 없이
`LocalConnection`이 `World`를 직접 부르는 모드)로 접속해 개발자 콘솔
명령(`give`/`store`/`tier`)으로 상황을 빠르게 만들었다.

- **1차 재현 시도**: Playwright의 `mouse.click(x, y, { modifiers: ['Shift'] })`
  로 시도했더니 게임이 `shiftKey`를 계속 `false`로 읽어서 아예 쉬프트클릭
  자체가 안 먹혔다 — **이건 Playwright 자동화 특유의 문제**였다
  (`keyboard.down('Shift')` → `mouse.click()` → `keyboard.up('Shift')`로
  바꾸니 정상적으로 `shiftKey: true`가 잡혔다). 이 방법으로 다시 재현했더니
  창고→인벤토리 퀵무브 자체는 **정상 동작**했다 — 최초 제보의 "인벤토리"
  케이스는 이 유닛 테스트+올바른 방법의 실제 재현 둘 다에서 재현되지 않았다.
- **2차: 충전 칸 시나리오 재현**: 사용자가 구체적으로 짚어준 "코어 티어
  업그레이드 → 충전 칸 증가 → 모달 안 닫고 그 칸에 넣기"를 그대로 재현했다.
  티어 1(충전 칸 1개 열림) → 그 칸에 재료를 넣어 충전 시작 → 모달 열어둔 채
  `tier 3`로 승급(충전 칸 3개로 증가) → 다시 재료를 넣으려 쉬프트클릭 →
  **재현됨**: 2·3번 칸이 계속 "잠김"으로 표시되고 클릭도 안 먹혔다.

### 3. 원인 특정 — Phaser Text 렌더링이 데이터 갱신을 못 따라감

`CorePanel.setChargeSlots()`에 로그를 심어 실측했다:

- 서버가 계산하는 `openChargeSlotCount()`(코어 티어 기반)는 **정확히 3**으로
  올라가 있었다.
- 스냅샷을 통해 클라이언트로 오는 `status.openChargeSlots`도 매 프레임
  **정확히 3**이었다.
- `CorePanel.setChargeSlots()`도 매 프레임 `openCount=3`을 정확히 받고
  있었다.
- 그 안에서 `label.setText('비었음')`을 호출한 **직후 `label.text` 속성을
  직접 읽어봐도 `'비었음'`으로 정확히 바뀌어 있었다.**

즉 **데이터도, 텍스트 오브젝트의 내부 문자열 값도 전부 정확했다** — 그런데
화면에 실제로 그려지는 픽셀만 이전 값("잠김")에 멈춰 있었다. Phaser의
`Text.setText()`가 캔버스 텍스처를 다시 굽는 내부 처리가 이 특정 순간(락 →
언락으로 바뀌는 그 한 번)에 씹히면, 그 뒤로는 문자열이 그대로라(매 프레임
같은 값 재대입) 다시 구울 계기가 없어 **영원히 고착**된다 — 이게 "모달을
닫았다 열면 고쳐진다"는 제보와도 맞아떨어진다(닫고 열면 텍스트 오브젝트가
새로 만들어져 강제로 다시 그려진다).

**해결**: `setText()` 뒤에 Phaser 내부 API `updateText()`(공개 타입엔 없어
캐스팅으로 호출)를 한 번 더 강제로 불러 텍스처를 무조건 다시 굽게 했다.
Playwright로 정확히 같은 시나리오를 재현해 **수정 전/후를 스크린샷으로
직접 비교**해서 고쳐졌음을 확인했다.

### 4. 같은 패턴을 쓰는 다른 칸에도 예방적으로 적용

이 버그의 본질은 "칸 여러 개를 매 프레임 `setText()`로 채우는" 공통 패턴에
있다 — `CorePanel`(충전 칸)뿐 아니라 `WarehousePanel`(창고 칸),
`QuickSlotBar`(퀵슬롯)도 정확히 같은 패턴을 쓴다. 원래 제보 문구("인벤토리로
가져오려 했을 때")는 이 계열 중 하나를 가리켰을 가능성이 높다(재현은
충전 칸에서만 됐지만). `theme.ts`에 `forceSetText()` 공용 헬퍼를 만들어 세
파일의 칸 라벨 갱신에 전부 적용했다.

- `packages/client/src/game/ui/theme.ts`: `forceSetText()` 헬퍼 신설.
- `packages/client/src/game/ui/CorePanel.ts`: 충전 칸 라벨을
  `forceSetText`로 교체(원 재현 지점).

  성공을 스크린샷으로 직접 확인. client typecheck·build + shared 전체
  566/566 + server typecheck·test(31) + lint 전부 통과.

## 참고 — 이번에 쓴 도구

이 세션에 Playwright + Chromium을 새로 설치해서 실제 브라우저로 재현했다
(`npx playwright install chromium`, 프로젝트 의존성에는 추가하지 않음).
정적 분석만으로는 "데이터는 맞는데 화면만 틀리다"는 렌더링 버그를 찾을 수
없었던 사례라, 비슷한 "논리적으로는 맞아 보이는데 화면이 이상하다"는
제보가 다시 나오면 같은 방식(실제 조작 재현 + 단계별 스크린샷·로그)을
우선 고려할 만하다.
