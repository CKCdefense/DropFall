# 64. 작업 보고서 — 지형 기반 자원 배치로 전면 교체 (게임 흐름 피드백 #4)

## 기획

기존 자원 노드(나무/돌) 배치는 코어를 중심으로 한 "군집(클러스터)" 방식이었다 —
클러스터 중심을 `[260,500]px` 띠 안에서 무작위로 고르고, 그 중심 주변에 노드를
흩뿌렸다. 사용자 피드백:

> 자원 스폰관련 -> 현재 맵이 랜덤 seed로 각 타일이 생성되는 구조인데 이 구조를
> 이용해서 각 타일(ex 사막, 초원 등등)에 자원이 생성될 확률을 넣어서 현재에
> 있는 자원 생성로직을 사용하지않고 랜덤확률로 자원이 배치되게 만들고싶음.
> 그러면서 최소-최대 자원 스폰양은 유지 - 유저 인원수에 따라 증가하도록 설계

논의로 확정한 사항(AskUserQuestion):

- **지형 렌더링이 아직 client/server 어디에도 안 붙어 있어도 그대로 진행** —
  `shared/terrain/terrain.ts`는 순수 결정론적 함수라 나중에 타일맵이 실제로
  그려져도 같은 시드를 쓰는 한 자동으로 맞아떨어진다.
- **지형-자원 매핑**: 나무 = grass/dirt, 돌 = stone.
- **배치 방식**: 클러스터링과 블렌딩하지 않고 **완전히 대체** — 타일마다 독립적인
  확률을 굴려서 배치한다.
- 최소/최대 스폰량은 유지하되 **인원수에 따라 증가**하도록 스케일링한다(기획서
  §10.2의 `기본값 × (0.6 + 0.4 × 인원수)` 공식을 자원 노드에도 재사용 — 사용자가
  이전 피드백 #2에서 말한 "3배"는 몬스터 드랍 자원이었지 채집 노드가 아니라고
  명시적으로 확인했다).

## 과정

### 1. `seedResourceOnTerrain()` 신규 구현

`world.ts`의 `seedResourceClusters()`를 제거하고 `seedResourceOnTerrain(type,
playerCount)`로 교체했다:

1. `scaledResourceTarget(type, playerCount)`으로 목표 개체수를 계산(`Math.round(기본값
   × (0.6 + 0.4 × 인원))`, 기본값은 기존과 동일한 나무 10 / 돌 6).
2. 이미 배치된 같은 타입 노드 수를 세서 부족분(`needed`)만 계산 — 0 이하면 즉시
   반환(멱등).
3. 맵 전체(128×128 셀)를 스캔해서 `topFullTerrainAt(cx, cy, terrainSeed)`로 지형을
   조회하고, 타입에 맞는 지형(`RESOURCE_TERRAIN`)이면서 코어로부터 `[260,500]px`
   띠 안에 있는 셀만 후보로 모은다.
4. 후보를 `shuffleInPlace`(Fisher-Yates, `this.rng()` 사용)로 섞은 뒤, 하나씩
   `RESOURCE_TILE_CHANCE`(5%)를 굴려 성공하면 배치 — 이미 배치한 노드와
   `MIN_NODE_SPACING`(36px) 이상 떨어져 있는지 확인하고, 목표 개체수에 도달하면
   중단한다.

기존 클러스터 상수(`WOOD_CLUSTER_COUNT` 등)는 전부 제거하고, 최소/최대 거리 상수는
`RESOURCE_MIN_DISTANCE`/`RESOURCE_MAX_DISTANCE`로 이름만 바꿔 그대로 물려받았다
(코어 건축 반경·야간 웨이브 반경과 얽힌 값이라 바꿀 이유가 없었다). 리스폰 시
재배치(`relocateRespawnedNode`)는 그대로 두되, 이제 "클러스터 중심"이 아니라
"노드 자신의 최초 배치 위치" 주변으로 되돌아가도록 `clusterX`/`clusterY`를 노드
자신의 좌표로 채웠다.

### 2. 생성자 vs `startColonies()` 분리 유지

자원 노드는 인원수를 몰라도 최소한은 있어야 하는 테스트/로컬 시나리오가 많아서,
콜로니처럼 생성자에서 완전히 빼지 않고 "생성자는 1인 기준으로 최소 배치, 인원이
확정되면 `startColonies(count)`가 모자란 만큼 보충"하는 구조를 택했다(멱등 설계
덕에 안전).

### 3. 지형 시드 — 두 번의 실패 끝에 고정 상수로 정착

지형 노이즈에 쓸 시드를 무엇으로 할지가 예상외로 까다로웠다:

- **1차: `this.rng()`에서 뽑기** → 생성자 맨 앞에서 rng를 한 번 더 소비해서, 그 뒤로
  이어지는 모든 게임플레이 랜덤(몬스터 스폰 등)이 한 칸씩 밀렸다. `seededRng(N)`을
  쓰는 기존 테스트 다수가 (지형과 무관한 것들까지) 깨졌다 — 예를 들어 Flow Field
  재라우팅 테스트가 "방향이 안 바뀐다"고 실패했는데, 원인은 전혀 다른 몬스터 스폰
  시퀀스가 밀린 것이었다.
- **2차: `Math.random()`으로 매번 다르게 뽑기** → 실행마다 지형(=자원 노드 위치)이
  달라지면서, 좌표를 하드코딩한 다른 테스트들과 **산발적으로**(실행할 때마다 다른
  테스트가) 충돌해 플레이키해졌다. 재현이 안 돼서 디버깅이 더 어려웠다.
- **최종: `private readonly terrainSeed = 875_309;` 고정 상수.** 지형 렌더링이
  아직 아무 데도 안 붙어 있어서(2026-08 시점 client/server 어디서도
  `topFullTerrainAt`을 안 씀) "게임마다 달라야 한다"는 요구 자체가 지금은 없다.
  나중에 실제로 지형을 그리게 되면, 그때 가서 방(room)마다 시드를 정하고
  클라이언트에 동기화하는 설계를 제대로 해야 한다(그때 비로소 "매판 달라야 한다"는
  요구가 생기기 때문). 그 전까지는 고정값이 제일 안전하고 결정론적이다.

### 4. `startColonies()` 안에서 호출 순서 버그 — rng 시퀀스가 콜로니 위치까지 밀림

자원 노드를 `startColonies(count)`에서도 인원수만큼 보충하도록 추가하면서,
처음에는 `this.seedResourceNodes(count)`를 `this.colonies.seed(count, this.rng)`
**앞에** 호출했다. `seedResourceOnTerrain`의 `shuffleInPlace`가 후보 타일을 섞느라
`this.rng()`를 추가로 소비하는데, 이게 콜로니 배치보다 먼저 일어나면서 콜로니가
소비하는 rng 시퀀스 자체가 밀려버렸다 — 같은 시드(`seededRng(1)`)로 만든
`World`인데도 콜로니 위치가 (자원 배치 알고리즘이 바뀔 때마다) 달라지는 부작용이
생겼다.

이게 `world-building.test.ts`의 "추격 타겟이 있어도 사거리 안에 막는 건축물이
있으면 그것부터 공격한다" 테스트를 깨뜨렸다 — 좌표를 못 박고 콜로니/몬스터
상호작용을 보는 테스트라, 콜로니 위치가 이전과 달라지면 몬스터가 애초에 원하는
지점에 있지 않게 된다. **해결**: `startColonies()`에서 `colonies.seed()`를
**먼저** 호출하고, 자원 노드 보충은 그 뒤로 옮겼다 — 자원 보충은 콜로니 위치와
무관하므로 순서를 늦춰도 안전하다.

### 5. 콜로니 트리클 스폰(피드백 #3)과의 상호작용 — 숨어있던 두 번째 버그

위 순서 수정 후에도 "건축물을 설치하면 직선 경로가 막힌 몬스터의 이동 방향이
바뀐다(Flow Field 재계산)" 테스트 하나가 계속 실패했다. `console.log`로 추적한
결과, 테스트가 `[...world.getMonsters().values()]`의 **첫 번째** 원소를 "웨이브
몬스터"로 가정하고 좌표를 강제로 옮겼는데, 실제로는 **콜로니 수호대**(`homeColonyId`
있음)가 잡혔다.

원인 체인:
1. 이 테스트가 배치하는 `near` 플레이어(500,500)가, 마침 이 시드에서 (523,582)에
   생성된 콜로니의 트리거 반경(240px) 안에 들어갔다(거리 ≈85px).
2. 이전 작업(피드백 #3, `docs/backend/62`)에서 추가한 트리클 스폰 덕에, 플레이어가
   콜로니 근처에 있기만 하면 저장분과 무관하게 수호대가 계속 나온다.
3. `spawnAtLeast(world, 1)`이 "몬스터가 1마리 이상"만 확인하다 보니, 웨이브 몬스터가
   아니라 이 수호대를 먼저 집어버렸다.
4. 수호대는 `tickGuard()` 경로(리시 안 플레이어 요격 + 귀환)를 타지, 테스트가
   검증하려는 코어 추격 Flow Field 경로(`tickMonsters()`의 core-direct 분기)를
   전혀 타지 않는다 — 그래서 벽을 세워도 방향이 안 바뀌었다.

이 문제는 **자원 배치와는 무관한, 순수하게 우연한 좌표 충돌**이다(콜로니 위치가
rng 시퀀스 변화로 이 시드에서 처음 이 자리에 오게 됐을 뿐) — 그런데 이 파일의
여러 테스트가 똑같은 패턴(`spawnAtLeast` + `[...values()][0]`)을 쓰고 있어서
잠재적으로 다른 테스트도 같은 방식으로 우연히 깨질 수 있는 구조적 취약점이었다.
**해결**: `spawnAtLeast()`가 수호대를 제외한 "웨이브 몬스터" 개수만 세도록 고치고,
`firstWaveMonster(world)` 헬퍼를 추가해 수호대가 섞여 있어도 항상 웨이브 몬스터를
집도록 했다. 이번엔 실제로 이 취약점을 밟은 테스트 한 곳만 새 헬퍼로 바꿨다(나머지
13곳은 `[colony]`를 함께 집어 콜로니 상호작용을 의도적으로 보는 테스트이거나, 이번
검증에서 실제로 깨지지 않았다).

### 6. 검증 중 발견한 과잉 수정 — "자원 노드를 전부 치우자"는 되돌림

초기 진단 단계에서, 실패한 3개 테스트가 전부 "코어 근처 좌표를 하드코딩해 놓고 건물/
몬스터를 박아 넣는" 패턴이라 자원 노드가 우연히 끼어드는 게 원인이라고 (틀리게)
추측하고, `createTestWorld()` 안에서 자원 노드를 전부 지우는 `clearResourceNodes()`를
전역으로 걸었다. 결과는 25개 실패로 악화 — 이 파일에는 `isolateNode()`로 실제 자원
채집 메커니즘을 보는 테스트도 섞여 있어서, 자원 노드를 통째로 없애면 그 테스트들이
채집할 대상을 못 찾고 죽는다. 전역 호출을 되돌리고, 위 §4·§5에서 찾은 진짜 원인
(rng 순서, 트리클 스폰 우연 충돌)을 고쳐서 해결했다 — 결과적으로 `clearResourceNodes`
헬퍼는 "울타리는 투사체를 막지 않고 통과시킨다" 테스트 한 곳에만 국소적으로 남았다
(그 테스트는 좌표 (260,0)/(350,0)를 정확히 자원 배치 반경 경계에 박아 놓고 투사체
통과만 보는 테스트라, 자원 노드가 실제로 그 자리에 우연히 설 수 있어 국소적 제거가
맞는 케이스였다).

## 결과

- `packages/shared/src/sim/world.ts`: 클러스터 기반 배치를 지형 기반 확률 배치로
  전면 교체. `startColonies()` 호출 순서를 콜로니 우선으로 정정.
- `packages/shared/tests/world-building.test.ts`: `spawnAtLeast`가 콜로니 수호대를
  제외하도록 수정, `firstWaveMonster()` 헬퍼 추가, 국소적 `clearResourceNodes()`
  적용(투사체 테스트 1곳), 타겟 리셋 추가(Flow Field 테스트 1곳).
- 재검증: `world-building.test.ts` 단독 20회 연속 재실행(76/76, 안정) +
  shared 전체 539/539 + server typecheck·test(31) + client typecheck + lint 전부
  통과. 검증 중 CPU 경합에 의한 타임아웃성 플레이크 1~2회 관측했는데, 이는
  `vitest.config.ts`에 이미 문서화된 기존 환경 이슈(무관한 원인)로 확인했다.

이로써 사용자가 요청한 4개 게임 흐름 피드백(공격 스탯 밸런스, 콜로니 트리클 스폰,
웨이브 인원수 스케일링, 지형 기반 자원 배치)이 모두 구현·검증 완료됐다.
