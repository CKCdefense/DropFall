# 작업 보고서 — 자원 노드 리스폰 재배치 + 몬스터 충돌 반경 버그 수정 + 스폰 최소거리 확대

> 스크린샷(코어 근처까지 붙어 있는 자원 군집)과 함께 세 가지를 이어서 받은
> 요청이다: (1) 자원 노드를 다 캐면 그 자리가 영구 장애물처럼 남지 않게 —
> 리스폰될 때 같은 군집 안 새 위치로, 플레이어와 안 겹치게. (2) 자원 군집
> 스폰 최소거리를 늘려서 코어 근처 이동 불편 해소. (3) 몬스터가 자원 노드를
> 뚫고 다니는 버그 수정. (3)을 조사하다가 backend/38에서 넣은 몬스터 하드
> 충돌 코드 자체에 진짜 버그(반경 누락)가 있었다는 걸 찾았다 — 아래 §2.4에
> 그 과정을 남긴다.

---

## 1. 기획 — 무엇을, 왜

원문 요청(스크린샷 첨부):

> "다캐면 움직일수있게해줘 기존위치에서 자원이 리젠되는게아닌 해당 군집에서
> 랜덤위치(플레이어위치랑 겹치지않는 로직도 추가)에 리젠"
> "다음으로 자원 스폰 최소거리 늘리기 스크린샷 기준으로 너무 가까워서 코어
> 근처 이동에 불편함 존재"
> "몬스터는 자원을 뚫고다니는 문제도 수정바람"

구현 전 확인한 설계 방향:

- **콜로니는 그대로 정적, 자원 노드만 동적으로 바뀐다.** backend/38에서
  "정적 오브젝트"는 콜로니/자원 노드/코어 셋 다 위치가 절대 안 변한다는
  전제로 `staticObstacleCells`를 생성 시 한 번만 계산해 캐싱했다. 이번
  요청으로 그 전제가 자원 노드 쪽만 깨진다 — 고갈되면 막지 말아야 하고,
  리스폰되면 새 위치로 옮겨야 한다. 콜로니는 "파괴"조차 위치를 안 바꾸므로
  (잔해가 계속 막는다) 그대로 정적으로 남긴다.
- **리스폰 재배치는 기존 군집 배치 인프라를 재사용한다.** 최초 시딩 때 쓰던
  `pickClusterNodePosition`(군집 중심 주변 지터 반경 안에서, 겹치지 않는
  위치를 재시도로 찾는 함수)에 "플레이어와도 안 겹침" 조건만 추가하면 리스폰
  재배치에도 그대로 쓸 수 있다.

## 2. 과정 — 어떻게 했나

### 2.1 리스폰 시 같은 자리로 안 돌아가게

`ResourceNodeEntity`에 `clusterX`/`clusterY`(노드가 속한 군집 중심, 노드
수명 내내 고정)를 추가했다 — `x`/`y`는 리스폰마다 바뀌지만, "같은 군집
안이어야 한다"는 제약을 리스폰 시점에 다시 계산하려면 원래 소속 군집을
기억해야 한다. `seedResourceClusters()`가 노드 생성 시 이 값을 함께 채운다.

`pickClusterNodePosition(centerX, centerY, placed, nodeRadius)`에 넷째
인자(`nodeRadius`)를 추가하고, 재시도 루프의 "형제 노드와 안 겹침" 조건에
"지금 접속 중인 플레이어와도 안 겹침"(`circlesOverlap(player, candidate,
HIT_RADIUS + nodeRadius)`)을 추가했다. 초기 시딩 시점엔 `World` 생성자가
항상 `addPlayer()`보다 먼저 실행돼 플레이어가 한 명도 없으므로 이 조건이
자동으로 무해하다 — 같은 함수를 리스폰에도 그대로 쓸 수 있는 이유다.

신규 `relocateRespawnedNode(node)`가 리스폰 순간 호출된다 — "이미 놓인
것"으로 **같은 군집의 살아있는 형제 노드만** 넘겨서(다른 군집이나 고갈된
노드는 겹쳐도 무관) `pickClusterNodePosition`을 재사용한다.

### 2.2 정적 장애물 셀을 콜로니(정적)/자원 노드(동적)로 분리

기존 `staticObstacleCells`를 `colonyObstacleCells`(콜로니 전용, 생성 시 1회
계산, 이름만 명확하게 변경)로 남기고, 신규 `resourceObstacleCells`(자원 노드
전용, **상태가 바뀔 때마다 재계산**)를 추가했다. `rebuildResourceObstacleCells()`가
살아있는(hp>0) 노드만 셀로 등록한다. 두 가지 트리거 지점에서 호출한다:

- **고갈 순간**(`applyMeleeHitToResourceNode`, hp가 0에 닿는 순간) — 그
  즉시 그 칸이 열린다("다 캐면 움직일 수 있다").
- **리스폰 순간**(`tickResourceNodes`) — `relocateRespawnedNode`로 옮긴
  뒤. 한 틱에 여러 노드가 동시에 리스폰될 수 있어 루프 끝에 한 번만
  호출하도록(`anyRespawned` 플래그) 배칭했다 — 노드마다 매번 부르면 낭비다.

`isBlockedForPlayer()`/`projectileHitsObstacle()`의 자원 노드 루프에도
`if (node.hp <= 0) continue;`를 추가해 플레이어/투사체도 고갈된 자리를 그냥
통과하게 했다.

### 2.3 클라이언트가 리스폰 이동을 그려주지 않던 문제

서버 로직만으론 부족했다 — `EntityRenderer.syncResourceNodes()`가
`sprite.setDepth(node.y)`만 매 스냅샷 갱신하고 **x/y는 스프라이트 생성
시점에 한 번만** 설정하고 있었다(예전엔 자원 노드가 절대 안 움직인다는
전제였으니 문제가 없었다). 리스폰으로 서버 위치가 바뀌어도 화면엔 예전
자리에 그대로 남는 버그였다 — `sprite.setPosition(...)`을 동기화 루프에
추가했다. `SnapshotInterpolator`는 원래부터 `resourceNodes`를 보간 대상이
아니라 최신값 그대로 통과시키므로(건축물과 동일), 리스폰은 순간 이동으로
보인다 — "펑 하고 새 자리에 나타나는" 연출이 리스폰이라는 사건과도 잘
맞아서 그대로 뒀다.

### 2.4 몬스터가 자원 노드를 뚫는 버그 — 진짜 원인

backend/38에서 몬스터용 정적 오브젝트 하드 스톱으로 만든
`findBlockingStaticObstacle(monster, range)`는 `range` 인자에 항상
`data.attackRange`(대부분 20px)를 그대로 넘겨서 "몬스터 중심에서 이 거리
안이면 막힌 것"으로 판정하고 있었다 — **몬스터 자신의 충돌 반경을 더하지
않는다.** 예를 들어 탱커(`hitRadius=9`)가 자원 노드(`hitRadius=14`)에
접근할 때 실제로 안 겹치려면 9+14=23px는 떨어져야 하는데, 검사 기준은
20px라 **3px는 이미 파고든 뒤에야 멈췄다.** 몸집이 작은 몬스터
(`hitRadius=6`)는 실제 필요 거리(6+14=20)가 우연히 `attackRange`(20)와
거의 같아서 버그가 잘 안 드러났고, 몸집 큰 탱커/보스에서만 눈에 띄게
파고들었다 — "자원을 뚫고 다닌다"는 사용자 신고와 정확히 일치한다.

원인은 애초에 `attackRange`를 재사용한 것 자체였다 — 건축물 쪽
(`findBlockingBuildingInRange`)은 "공격할지 말지"를 판단하는 용도로
`attackRange`를 쓰는 게 맞지만, 자원/콜로니는 공격하지 않고 그냥 멈추기만
하므로 필요한 잣대가 다르다. 플레이어 쪽(`isBlockedForPlayer`)은 처음부터
`HIT_RADIUS + 노드반경`처럼 두 반경의 합을 정확히 쓰고 있어서 이 버그가
없었다 — 몬스터 쪽만 놓친 것이었다.

수정: `findBlockingStaticObstacle`에서 `range` 매개변수를 없애고, 후보마다
`monsterRadius(monster) + 후보자신의반경 + STATIC_OBSTACLE_STOP_BUFFER(4px
여유)`를 기준으로 판정하도록 바꿨다. 자원 노드는 `hp <= 0`이면 후보에서
제외(고갈된 노드는 몬스터도 막지 않는다 — §2.2와 동일 원칙). 두 호출부
(`tickMonsters`의 추격/코어행 분기)에서 `attackRange` 인자를 뺐다.

## 3. 결과 — 검증

```bash
pnpm --filter @dropfall/shared test        # 17 files, 254 tests 전부 통과(신규 7개)
pnpm --filter @dropfall/server typecheck   # 순차 실행(동시 -r 실행 시 이 환경 OOM)
pnpm --filter @dropfall/client typecheck
pnpm lint      # 에러 0
pnpm build     # client(vite)/server(tsup) 전체 통과
```

`world-building.test.ts`에 추가한 신규 테스트 7개:

- 탱커(반경 큰 몬스터)가 자원 노드에 접근해도 실제 충돌 반경(9+14=23px)
  안으로는 못 들어간다는 걸 500틱 동안의 최소 거리로 확인(§2.4 버그의
  회귀 테스트 — 수정 전 코드였다면 20px에서 멈춰 실패했을 것).
- 고갈된(hp≤0) 자원 노드는 플레이어/투사체/몬스터 중 어느 것도 막지 않는다
  (3개, 기존 "막는다" 하드 충돌 테스트와 대칭되는 "안 막는다" 버전).
- 노드가 고갈→리스폰되면 원래 좌표가 아닌, 같은 군집 중심 지터 반경 안의
  새 위치로 옮겨간다.
- 리스폰 위치가 군집 중심에 서 있는 플레이어와 겹치지 않는다.
- 모든 자원 노드가 코어(원점)에서 최소거리(260-80=180px 바닥값) 이상
  떨어져 있다(스폰 최소거리 확대 검증).

## 4. 다음 작업

- **밸런스 값 전부 임의값** — `CLUSTER_MIN_DISTANCE`(260)/`CLUSTER_MAX_DISTANCE`
  (500)/`CLUSTER_JITTER_RADIUS`(80)/`STATIC_OBSTACLE_STOP_BUFFER`(4) 모두
  플레이테스트 후 조정 대상이다. 특히 리스폰 지터가 군집 안 다른 노드나
  플레이어와 계속 안 맞으면(좁은 반경에 노드가 몰린 군집) 8회 재시도 뒤
  겹친 채로 배치될 수 있다 — 실제로 자주 발생하면 재시도 횟수나 지터
  반경을 늘려야 한다.
- **FlowField 재계산 빈도 증가** — 리스폰/고갈마다 `recomputeFlowField()`를
  부르는데, 자원 노드 개수가 많고 리스폰이 잦아지면(멀티플레이 동시 채집)
  비용이 누적될 수 있다. 아직 실측하지 않았다 — 플레이테스트로 체감 랙이
  있으면 배칭 폭을 더 넓히는 최적화가 필요하다.
