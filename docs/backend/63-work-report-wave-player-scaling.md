# 63. 몬스터 웨이브 인원수 스케일링 (작업 보고)

> 게임 흐름 피드백 4건 중 #2("몹 숫자가 너무 적다, 자원 수급처 부족") 처리. 순서:
> 1(공격 스탯)→3(콜로니)→**2(이 작업)**→4.

## 1. 기획 — 무엇을, 왜

기획서(`01-game-design.md` §10.2)는 "몬스터 수 = 기본값 × (0.6 + 0.4 × 인원수)" 스케일링을
전제로 하는데, 코드로 확인해보니 **실제로는 인원수 스케일링이 아예 구현돼 있지 않았다**
(`wave.ts`에 `playerCount`/`players.length` 참조 0건) — `waves.json`에 박힌 고정 숫자가
인원과 무관하게 그대로 나갔다.

사용자 피드백 원문의 "3배가량"은 재확인해보니 나무/돌 노드가 아니라 **몬스터 처치로
얻는 자원(에너지 등) 수급 부족**을 가리킨 것이었다 — 즉 몬스터 자체를 늘리면 자연히
해결되는 문제다. 나무/돌 노드는 이번 작업 범위에서 뺐다.

두 질문으로 정확한 수치를 정했다:
- 몬스터 수: **기본값 3배** + **인원수당 +100%(설계서 0.4 계수를 2로 확장)**

## 2. 과정 — 어떻게 했나

### 2.1 데이터
`waves.json`에 `playerScaling: { baseMultiplier: 3, base: 0.6, perPlayer: 2 }` 추가.
최종 스폰 수 = `round(spawns[type] × baseMultiplier × (base + perPlayer × 인원수))`.
`data/index.ts`에 스키마(`WavePlayerScalingSchema`) 반영.

웨이브1(원래 잡몹 8) 기준 실제 스폰 수:
| 인원 | 배율 | 스폰 수 |
|---|---|---|
| 1 | 3×2.6=7.8 | 62 |
| 2 | 3×4.6=13.8 | 110 |
| 3 | 3×6.6=19.8 | 158 |
| 4 | 3×8.6=25.8 | 206 |

### 2.2 구현
`WaveManager`가 이제 `playerCount: () => number` 콜백을 받는다(`rng`와 같은 주입 패턴).
`World`가 `new WaveManager({ playerCount: () => this.players.size })`로 실제 접속 인원을
넘긴다. `beginNextWave()`에서 `entry.spawns`의 각 타입 수를 스케일링해서 스폰 큐를 만든다.

**엘리트 굴림 횟수(`entry.elite.count`)는 스케일링에서 뺐다.** 그대로 곱하면 "낮은 확률로
어쩌다 하나 나오는" 엘리트가 인원 늘어날수록 "거의 매 판 여러 마리 확정"으로 바뀌어버려서
— 엘리트라는 설계 의도(희귀한 긴장감) 자체가 깨진다. 일반 잡몹은 물량으로 미는 대상이지만
엘리트는 아니라는 판단.

### 2.3 테스트가 두 군데 깨졌다(둘 다 예상된 것)
- `wave.test.ts`의 `baseTotal`/`maxTotal` 헬퍼가 원본 숫자를 그대로 썼어서, 스케일링 후
  실제 스폰 수와 안 맞아 깨졌다 → 헬퍼에 같은 스케일링 공식을 반영(1인 기준, 이 테스트
  파일은 인원을 따로 안 정하므로 `WaveManager` 기본값 1명).
- `drainMinionSpawns` 헬퍼의 조기 종료 조건(`alive >= baseTotal && 반복 60회 넘으면 멈춤`)이
  원래 총원(8~40대)을 기준으로 잡은 값이라, 스케일링 후 총원(최대 200대 후반)에 도달하는
  데만도 60회를 넘겨서 **도달하자마자 즉시 멈춰버렸다** — 그 순간 엘리트 여분이 아직 큐에
  남아있으면 스폰 큐가 안 비고, 큐가 안 비면 밤이 안 끝나 이후 보스 소환 테스트가 전부
  깨졌다. `manager.pendingSpawnCount`로 큐가 실제로 비었는지 직접 확인하도록 고쳤다.
